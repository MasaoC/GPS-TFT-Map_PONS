## 2. 実機確認の手順

### Step 0 — **旧基板（v7 / BNO085）で 1 回飛ばす**

★ **SCH16T に移る前にこれをやること。** 計画書 §4 の 5 番。
0.986 でドライバを `imu_bno08x.cpp` へ割ったので、
「**抽象化しただけで挙動が変わっていない**」ことを実機で確かめておく。

これをやっておくと、SCH16T を足したあとに出た不具合が
**「抽象化のせい」か「SCH16T のせい」か切り分けられる。**
飛ばさずに先へ進むと、両方を同時に疑うことになる。

- `PONSv7` ブランチのファームで（2026-10-23 にブランチを分けたので、このブランチでは v7 基板は動かない）
- 見るもの: 姿勢（ロール・ピッチ・ヨー）、バリオの V/S、60 秒ログの
  `gapmax=` と `raw GYR/ACC`、`[Hz]` 行
- 比較対象: 0.985 以前のログ。**値が変わっていなければ合格**

PC 側で確認できる分は 2026-10-14 に済み（`tools/attitude_test` 全 PASS、
V7 / V71 の両ビルド OK）。残りは実機でしか見られない。

### Step 1 — 配線（v7.1 基板 + ブレイクアウト）

ブレイクアウト（`kicad/IMU_murata`）はフレキ基板で、尾の先の金端子 J3 を本体の J6 へ**直接挿す**。
別の FPC ケーブルは使わない（廃止した）。

| | |
|---|---|
| 接続 | 本体 **J6**（Molex 200528-0080, 8pin FPC）にブレイクアウトの尾（**J3**）を挿す |
| ピン順 | ブレイクアウト J3: `1=+3V3 2=RESET 3=MOSI 4=CS 5=SCK 6=SYNC 7=MISO 8=GND`。本体 J6 は**逆順**（`1=GND … 8=+3V3`）で、挿すと **J6-n ↔ J3-(9-n)** が接する。**1:1 ではない** |
| 通電前 | **J3 を J6 に挿した状態で、テスターで J6-8 と J3-1（+3V3）、J6-1 と J3-8（GND）の導通を確かめる**。逆だと SCH16T に電源が逆に入る |
| 本体 GPIO | `CS=41 / SCK=42 / MOSI=43 / MISO=44 / EXTRESN=45 / DRY=46`（SPI1 の正規割り当て） |

★ **ブレイクアウトの R2（CS–GND の 4.7k）は実装しない。** CS は負論理なので、
プルダウンすると MCU が駆動していない間セレクト状態になる。
R1（EXTRESN のプルアップ）は実装する。詳細は
[tools/sch16t_test/README.md](../tools/sch16t_test/README.md) の「配線」。

### Step 2 — 焼く

このブランチは v7.1 専用（2026-10-23 に分けた）なので、基板を切り替えるスイッチは無い。
そのままビルドして焼けば `imu_sch16t.cpp` が動く。

**起動ログで見るもの（0.991 のドライバが出す行）:**

| 出る行 | 意味 |
|---|---|
| `[IMU] SCH16T-K01 ready. chip responded in N ms` | **成功。** N が実際の立ち上がり時間 |
| `[IMU] SCH16T: ASIC_ID unreadable (check J6 wiring / SPI1 pins)` | 配線か SPI1 のピン |
| `[IMU] SCH16T COMP_ID 0x.... != K01 0x0023`（log.txt） | 別品種。感度が違うので使わない |
| `[IMU] SCH16T verify NG dyn=.. filt=.. STAT_SUM=0x....`（log.txt） | 設定が入っていない |
| `[IMU] SCH16T init retry` | 1 回目が失敗して 2 回目を試した |
| `[IMU] SCH16T pins are UNSET — check settings.h` | `settings.h` の `SCH16T_PIN_*` が UNSET になっている |

- **起動画面のセンサー行** — NG なら SPI が成立していない
- `#warning "... DO NOT FLY."` は**まだ出る**。Step 5 まで通したら消す

★ **`[IMU] SCH16T init retry` が毎回出るなら立ち上がり待ちが足りていない。**
単独テストでは実測 1ms だったので、出るとしたら本体側の電源の立ち上がりが遅い。
`SCH16T_READY_TIMEOUT_MS` ではなく **電源を疑う**（待ちの上限は 1 秒ある）。

★ うまくいかないときは **本体を疑う前に単独テストへ戻る**。
Pico 2 + `tools/sch16t_test` で `z` → `t` → `i` → `r` を通せば、
チップ・配線・フレーム層のどこが悪いかが分かる。本体のドライバを
デバッグするより圧倒的に速い（単独テストを作った理由がこれ）。

### Step 3 — 静止確認（机の上）

| 見るもの | 期待 |
|---|---|
| 姿勢 | ロール・ピッチが 0 付近で安定。水平化が効いて `ready=1` になる |
| バリオ V/S | 0 付近。デッドバンド内で鳴らない |
| 60 秒ログ `raw GYR / ACC` | **250Hz 付近**（`IMU_POLL_INTERVAL_US` = 4ms）。0 なら引き取れていない |
| シリアル `read rate too low` | **出ないこと**。出たら LPF2 の最小推奨 150Hz を下回っている |
| 60 秒ログ `gapmax=` | 数 ms 台。数十 ms に伸びたらどこかで飢えている |
| IMU/ESKF 画面の融合出力行 | **`---` に縮退していること**（`imu_caps()` が 0 を返すので） |

★ **融合出力の行に `0.0` が出ていたら囲い忘れ。** 姿勢比較の行なら
0 は「水平で北向き」というもっともらしい値なので、黙って誤表示になる。

★★ **センサーの向き（マウント回転）を測り直す。** `settings.h` の `IMU_MOUNT_Q*` は
**v7 の BNO085 で測った値のまま**で、SCH16T（IMU 基板）の向きでは測っていない。
同じコメントにある 3 点（水平・機首を真下・右翼を真下）で生加速度（IMU/ESKF 画面 2/3 の
`Accel raw`）を読み、違っていたら差し替える。違ったままだと**ロールとピッチが入れ替わったり
符号が逆になったりする**。差し替えたら `tools/imulog/decode_imulog.py` の `MOUNT_Q` も同じ値にする（PC 側の解析が同じ変換を使うため）。

★★ **ESKF のサンプル間隔と時定数を確かめる。** SCH16T はジャイロを 250Hz（4ms）で渡すが、
`attitude.cpp` の間隔推定の範囲と ESKF の「1 サンプルあたり」のゲイン（`ESKF_RELEVEL_GAIN` など）は
50Hz（`IMU_RATE_GYRO_HZ`）を前提にしている。4ms は間隔推定の範囲（0.2〜5 倍＝4〜100ms）の
**下限ちょうど**で、外れると間隔は初期値の 20ms のままになり、回転を 5 倍に積分する恐れがある。
机の上で本体を 90 度回して ESKF の角度が 90 度動くか、静止中の再水平化が 1 秒前後で効くかを見る。

### ★★ 250Hz が本当に出るか — ここが Step 3 の本題

**CPU は問題にならない。** 単独テストの実測（1MHz で 1698 サンプル/秒 = 8 フレームあたり
589µs）から 1 フレームの非 SCK オーバーヘッドは **25.6µs**。本体の 5MHz では
SCK が 9.6µs なので 1 フレーム 35.2µs、**1 サンプル 7 フレームで 246µs**。
250Hz なら **61.5ms/秒 ＝ Core0 の約 6%**。
★ SPI を 10MHz へ上げても 5.3% にしかならない（**オーバーヘッドが支配的**）ので、
クロックは効くレバーではない。効くのはフレーム数（温度を毎回読まないのが 12.5%）。

**効くのは loop() の周回**。ポーリングは 4ms のゲートなので、
**実効レート = min(250Hz, `imu_drv_service_if_due()` が呼ばれる頻度)**。

- 平常時は 4ms ゲートが律速 → 250Hz 出る
- **地図描画中は `gapmax` 実測 40ms 前後**（GPS_TFT_map.ino のコメント）。
  道路の多いタイルでは 100ms に達することもある → その窓では 10〜25Hz
- 100ms の停止が 2Hz で起きると 20% が停止 → 平均 **約 200Hz**。
  **LPF2 の最小推奨 150Hz に対して 33% の余裕**（LPF1 の 200Hz では余裕ゼロだった。
  これが LPF2 を既定にした決め手）

### 穴の出どころ — `imu_service_if_due()` はタイル単位

`src/vectormap.cpp:259` で**タイル 1 枚ごと**に呼んでいる。

```c
imu_service_if_due();                                      // ← タイル単位
const uint8_t* p = vm_blob + t->blob_off;
while (p < end) p = vm_draw_record(p, t, lod, &proj, cls); // ← ここでは呼ばれない
```

**道路が多いタイル 1 枚を描いている間は 1 回も引き取らない。** これが `gapmax` が
40ms に伸びる理由で、密なタイルなら 100ms もあり得る。

### 100ms 止まると SCH16T のデータはどうなるか

**欠落する。** デシメーション出力（`RATE_X2` など）は**単一のレジスタ組で FIFO ではない**
ので、チップは 1.39ms ごと（721Hz）に上書きし続ける。100ms なら約 72 サンプルが
作られて上書きされ、復帰時に読めるのは**最新の 1 つだけ**。

★★ **ただし BNO085 とは障害の種類が違う。**

| | BNO085 | SCH16T |
|---|---|---|
| 100ms 止まると | レポートが溜まる | 出力レジスタが上書きされる |
| 復帰後 | **ジャイロが化ける**（3 軸が 1 つの値の符号違いのコピー） | **最新の正しい値が 1 つ** |
| 障害の種類 | 静かなデータ破壊（バリオが暴れる） | サンプル数が減るだけ |

CLAUDE.md の「BNO085 の読み出しを飢えさせない」が必要だったのは、溜まったレポートが
**化ける**から。**SCH16T には溢れるキューが無いので、この障害は構造的に起きない。**

★ **実測の裏付け**: 単独テストの `c` は **5Hz**（ODR 721Hz の 144 分の 1）で読むが、
28 行すべてまともな値で **`<<BAD` が 1 つも付かなかった**。つまり ODR よりずっと遅く
読んでも、オーバーランのフラグがステータスビットを汚して不良フレームになることはない。

100ms の穴が ESKF に与える誤差は、最新のレートを 100ms ぶん積分する分だけ。
レートが一定なら誤差ゼロ、6°/s の旋回に入るところでも最大 0.3° 程度。
1 秒の通信途絶しきい値にも余裕がある（ドライバに「呼び出し間隔が空いた回は見送る」
ガードが BNO085 と同じ形で入っている）。

### `raw GYR` が 150Hz を下回っていたら

**`imu_service_if_due()` を `while (p < end)` の中へ移す**（`src/vectormap.cpp`）。
穴が 1 レコード分に縮まる。周期内なら即戻る関数なので安い。

★ **ただし測ってから入れること。** SCH16T では穴の代償が「サンプルが減る」だけで
破壊ではなく、LPF2 で 33% の余裕がある。レコードごとの呼び出しは 1 タイルに
数百〜千回増えるので、**実証済みの描画経路をデータ無しで触らない**。

### Step 4 — 走行（車載）

姿勢 ESKF の本番検証。0.984 の Phase 2 と同じ取り方をする。

- **生 IMU ログ（`IMULOG_RAW_REPORTS_ENABLED`）を有効にして取る。**
  そのとき `IMU_POLL_INTERVAL_US` が 250Hz 側になることを確認（§下の罠）
- 見るもの: 旋回中のロール、加減速中のピッチ、GNSS 断中の保持
- **`KF_R` / `KF_Q_VEL` の再測定**（計画書 §4 の 6）。
  加速度ノイズが BNO085 の 1/4.7 になるので、**観測ノイズの前提が変わる**

### Step 5 — 飛行

Step 0〜4 が通ってから。

## 3. 踏みそうな罠（単独テストで分かったもの）

- **★★ リセット直後は「CRC は正しいがデータが 0」のフレームが返る。**
  固定 `delay()` だけで進むと**設定書き込みが黙って捨てられる**。
  `ASIC_ID` が 0x0000/0xFFFF 以外になるまで待つこと（単独テストの
  `wait_chip_ready()`）。**CRC では検出できない**のがこの罠の厄介さ。
  実機ではコールドスタートで 1ms、暖まった状態の再初期化で 0ms だった
- **`CTRL_USER_IF` は read-modify-write。** リセット値が 0x200C で、素で書くと
  `FTREE_TDEL` / `MISO_SR_CTRL` / `DRY_SR_CTRL` を潰す
  （データシートが "not supported by Murata" と書いている側になる）。
  **PX4 のドライバはこれを踏んでいる**ので参考にするときは注意
- **読み出しは 1 フレーム遅れる。** 先頭の捨てフレームを落とすと、
  全軸が 1 つ前のレジスタの値になる（`gx` に前回の何かが入る形で静かに壊れる）
- **`EOI` 後は設定を変えられない**（ソフトリセットと `SYS_TEST` 以外ロック）。
  フィルターやレンジを変えたければリセットからやり直す
- **`DRY_SYNC` を出力にしないこと。** SYNC 入力との兼用ピン
- **`DYN_*` に `'000'` を書かないこと**（CTRL_RATE / CTRL_ACC12 では "Undefined"）
- **ODR は「DRY の回数」ではなく「最短周期」で見る。** DRY は
  「更新 → 最初の読み出し」の間だけ High なので、読み出しと更新の位相が重なると
  立ち上がりを取りこぼし、**回数は必ず過少に出る**（実測で期待の 77% に見えた）
- **`RATE_DCNT`(0x11) / `ACC_DCNT`(0x12) は「測定しているか」の判断に使えない。**
  init 成功・`STAT_*` 全部 0xFFFF の状態でも 0->0 のままだった。
  この 2 本は PX4 のヘッダに無く番地の根拠がデータシートだけ。
  **測定の有無はデータレジスタを直接見ること**
- **ジャイロの感度は 1g 検証では確認できない。** 加速度の感度は品種共通なので、
  `|a|/g` が 1.000 に乗っても**ジャイロが 16 倍ずれている可能性を否定できない**。
  実回転の積分（単独テストの `G`）が唯一の手段
- **★ `IMU_POLL_INTERVAL_US` の 33Hz 側は SCH16T では使えない。**
  `IMULOG_RAW_REPORTS_ENABLED` が無効だと 33Hz になるが、それでは
  **LPF2（13Hz）の最小推奨 150Hz すら満たせず、阻止域のノイズが折り返す**。
  BNO085 は「レポートを要求する」方式なので間引いてよかったが、
  **SCH16T は取りに行く方式なので読み出しレートがそのまま信号品質を決める**
