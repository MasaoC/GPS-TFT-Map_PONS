## 0. ひとことで

- 大会の配信（OBS）で、**パイロットが見ている画面**を流したい。
- 機体の画面は、ボートの受信機が無線でミラーしている（[pons_link.md](pons_link.md) §5）。その受信機を USB-C で Mac / PC につなぎ、
  Re:PONS から `PONS:LIVE,ON` を送ると、**受けたテレメトリを 1 発ごとに USB へ横流しする**。
- Re:PONS は受けた値で**機体の地図画面（縦 240×320）を、本体と同じ見た目・同じベクター地図・送信機の縮尺で canvas に描き直す**。
  画面の外の帯に、ボートで受けた受信強度と機体までの距離を出す。OBS は Chrome の窓を取り込む。
- **受信機だけの機能。** 送信機につないでも流さない。
- 受信機は今までどおり動く（ミラー表示・音・`received/` の記録）。**PC 接続の画面（`MODE_PCCONNECT`）には入らない。**
  受信機の画面には、流していることが分かる小さな `LIVE` の印を出す（§4.6）。
- 流すのは 3 種類（§3）:
  1. 受信機が組み立てた **LinkTelem**（数字）
  2. 受信機が画面のために決めた**判断**（目的地・距離・コース警告・大きい枠の種類など）
  3. **受信機自身の状態**（受信強度・NO SIGNAL・ボートの位置）

  **PC は描くだけで、判断をし直さない。**
- 無線は 1 秒に 1 回しか届かない（アッパーは 1.2〜3.5 秒）。位置と向きの動きは 1 発遅らせて間をつなぐ（補間する。数字は補間しない。§5.5）。
- 音（バリオ・案内・警報）は **Re:PONS では鳴らさない**。受信機が鳴らしている音をそのまま配信に乗せる（マイク・ライン。§10.3。2026-11-24 に決めた）。

## 1. 守ること

### 1.1 受信機の本来の仕事を変えない
- LIVE で変わるのは「USB へ行を書く」ことだけ。ミラー表示・警報と音・`received/` の記録・無線の受け方（`link_poll_radio()`）・
  描き直しの時刻（`link_draw_window_ok()`）は変えない。
- **`PONS:CONNECT` を使わない。** PC 接続の画面に入ると、受信機の画面が「USB SERIAL LINK ACTIVE」に替わり、`received/` の記録も止まる
  （[pons_webserial_protocol.md](pons_webserial_protocol.md) §3）。`PONS:TIME` / `PONS:DBD` と同じく、CONNECT なしで受けるコマンドにする。
- PC から変えられるのは LIVE の開始・停止だけ。受信機の設定・表示・航法を LIVE から変える口は作らない。

### 1.2 Core0 を USB で止めない
- arduino-pico 4.5.1 の `SerialUSB::write()` は、PC がポートを開いたまま読まないと、**送信バッファ（256 バイト）が空くまで最大 1 秒待つ**
  （`cores/rp2040/SerialUSB.cpp`。DTR が立っている間）。Core0 が 1 秒止まると、IMU の受け取り（`drain=`）・描き直し・無線の受信が遅れる。
  ブラウザのタブが裏で止められた、JS が固まった、などで普通に起きる。
- なので **LIVE の行は `Serial.availableForWrite()` を見て、行がまるごと入るときだけ書く**。入らなければ RAM の小さなリング（1〜2KB）に
  溜めて次の周回に回し、リングも溢れたら古い行から捨てて数える（60 秒ログに `LIVE: dropped=`）。**LIVE の行を `Serial.print` で直接書かない。**
- 1 行は 200 バイト以内にする。行を途中で切って書くと、ほかの返事（`PONS:TIME,OK` など）が行の間に挟まる。

### 1.3 配信にボートの値を機体の値として出さない
- CLAUDE.md の「ミラー中に自機の状態を混ぜない」の裏返し。受信機は 10 秒途切れると自機（ボート）の GNSS・気圧の画面に戻る（pons_link.md §5.4）。
  そのときの受信機の画面の数字は**ボートの値**なので、配信の画面へ流さない。
- 判断の行（§3.2 の `LN`）はミラー中だけ出す。途切れている間、Re:PONS は**最後に受けた機体の画面を灰色にして `NO SIGNAL` と経過秒**を出す。
- 同じ理由で、受信機のリプレイ中・デモ中（`link_rf_suppressed()`）は状態の行（`LS`）しか流さない。

### 1.4 判断は本体の 1 か所で（PC は描くだけ）
- 目的地の照合（`dest_id`）・Auto10km の折り返し・コース警告・大きい枠（Pavg / TAS / GROUND の線）・取消線は、受信機がもう計算している
  （pons_link.md §5.1、tas.cpp の `tas_header()`）。**JS で計算し直さない。** attitude.cpp と eskf.py のような二重実装は、片方だけ直したときに食い違う。
  配信の上では、食い違っても誰も気づかない。受信機が画面のために決めた結果を、そのまま行に載せる。
- PC が自分で計算するのは描くための幾何だけ（緯度経度を画面の点にする・補間）。

## 2. 全体の形

```
 機体 PONS（TX）
   │ LoRa 32 バイト / 1Hz（アッパーは 1.2〜3.5 s）
   ▼
 ボート PONS（RX）─ 画面のミラー・音・received/ の記録（今までどおり）
   │ USB-C（CDC）  PONS:LT / LN / LS の行（§3）
   ▼
 Mac / PC の Chrome ─ Re:PONS のライブ画面（canvas に機体の地図画面を描く）
   │ ウィンドウのキャプチャ
   ▼
 OBS ─ カメラの映像と重ねて配信
```

- 受信機はボートでもプラットホームでもよい（受信モードならどれでも）。
- Mac / PC が受信機に給電するので、受信機の電池は気にしなくてよい。

## 3. 何を流すか

### 3.1 案の比べ

| 案 | 中身 | 良い | 悪い |
|---|---|---|---|
| A. TFT の画面そのもの | 描いた絵を USB で送る | 見た目が完全に同じ | フレームバッファが無い（TFT へ直接描いている）。作ると RAM 150KB と Core0 の時間を食う。縮尺は受信機のまま |
| B. 電波の 32 バイトだけ | 受けたフレームをそのまま | ファームはほぼ何もしない | 回転枠の組み立てと時刻の繰り上げ（link_wire2.h）を JS で作り直す。目的地・警告などの判断も JS で（§1.4 に反する） |
| **C. LinkTelem ＋ 判断 ＋ 受信機の状態**（推奨） | 受信機が組み立てた値と、画面のために決めた結果 | JS は固定の並びを読むだけ。判断は本体の 1 か所 | 判断の行の中身を決める手間。LinkTelem の並びを変えたら JS も直す（`LINK_PROTO_VER` で止める） |
| D. `received/` の CSV の行 | SD に書く行と同じ | Re:PONS は CSV を読める | 目的地・ナビモード・縮尺・status の列が無い。行を作るのは Core1（SD の都合で止まる） |

**C にする。** 電波の 32 バイトは流さない（叩き台では記録用に流すつもりだったが、Re:PONS が使わないので 2026-11-24 にやめた。§10.5）。

- **電波の 32 バイトと LinkTelem は別物。** 電波に載るのは 32 バイト（毎回の「核」＋3 バイトの「回転枠」。回転枠は 8 発で一周）。
  LinkTelem は、受信機がそれを受けるたびに回転枠の値を覚えて組み立て直した、メモリの中だけの構造体（いまは 69 バイト）。
  描くのに使うのは LinkTelem（`LT`）。

### 3.2 行（叩き台）

すべて `PONS:` で始まる 1 行。数字は 10 進、バイト列は 16 進。
**作ったときの形は [pons_webserial_protocol.md](pons_webserial_protocol.md) §4 (9) が正**（下の表は叩き台のまま残す。2026-11-24 に Re:PONS が使わない欄と `LR` を削った。§10.5）。

| 行 | いつ | 中身 |
|---|---|---|
| `PONS:LIVE,OK,ON,<版>,<LINK_PROTO_VER>,<印>,<sizeof(LinkTelem)>,<mode>,<group>,<ch>,<sf>` | `LIVE,ON` の返事 | Re:PONS は版と並びが合うかを見る。合わなければ「Re:PONS が古い / ファームが古い」と出して描かない |
| `PONS:LIVE,DEST,<番号>,<dest_id>,<緯度>,<経度>,<名前>` …… `PONS:LIVE,DEST_END,<件数>` | 返事のすぐあと | 受信機の目的地の一覧（内蔵 4 つ＋ destinations.csv。パイロンの上書きの後）。地図に目的地・パイロンを描くため |
| `PONS:LT,<ms>,<rssi>,<slot>,<known>,<LinkTelem>` | 自分のグループのテレメトリを受けるたび | 回転枠を組み立てた後の `s_rx.t`（いまは 69 バイト・`LINK_PROTO_VER` 8。**2026-11-23 だけで 69 → 70 → 69 と 2 回変わった**ので、版と大きさで必ず確かめる）。`known` は回転枠 8 つのうち受けたもの（8 ビット。下の注） |
| `PONS:LR,<ms>,<32 バイト>` | 同じ | 電波のフレームそのまま（記録用） |
| `PONS:LN,<ms>,<seq>,...` | そのフレームで描き直したあと（ミラー中だけ） | 画面の判断。目的地（受信機の側の番号）・ナビモード・Auto10km の往路/復路・目的地までの距離と方位・コース警告・大きい枠の種類（`tas_header()`）と値・GROUND の札と WAIT 秒・取消線の理由 など |
| `PONS:LS,<ms>,...` | 1 秒ごと | 受信機の状態。ミラー中か / NO SIGNAL / 最後に受けてからの ms / 直近 10 秒の RSSI と本数（受信機の画面と同じ値）/ 受信率 / DUP SENDER / GROUP X FOUND / リプレイ中 / ボートの fix / 機体までの距離（`received/` の `dist_m` と同じ計算）/ 捨てた行の数 |
| `PONS:LIVE,OFF,<理由>` | 止めたとき | `CMD`（`LIVE,OFF`）/ `CONNECT`（PC 接続に入った）/ `MODE`（受信モードでなくなった） |

- **`LN` の中身は、描く関数が読んでいる値をそのまま並べる。** 作るときに `draw_header()` / `draw_gs_track()` / 地図まわり / `draw_footer()` が
  読む値を洗い出して決める（ここでは一覧を決めきらない）。
- 受け始めは、回転枠がそろうまで（ローワーで 8 秒、アッパーで最大 28 秒）目的地・縮尺などが分からない。LinkTelem には「分かっているか」が無い
  （0 のまま）ので、受信機の `link_rx_slot_known()` を `known` に添える（CLAUDE.md の「have ビットの無い項目は `link_rx_slot_known()` を見てから使う」と同じ理由）。
- `ms` は受信機の `millis()`。PC は自分の時計で描くので、順番と間隔を知るためだけに使う。
- 別のグループのフレームと、時刻の助け合いのビーコン（印 `0x58`）は流さない（叩き台では `LS` に「別のグループを見た」を出すつもりだったが、Re:PONS が使わないので出さない。§10.5）。

### 3.3 量
- 1 秒に `LT` 約 160 バイト・`LN` 100〜150・`LS` 約 50 ＝ 約 0.4KB/s。USB の Full Speed には何でもない。
- 1 行は 200 バイト以内（§1.2）。

## 4. 本体（ファーム）

### 4.1 始まりと終わり
- `PONS:LIVE,ON` / `PONS:LIVE,OFF`。`PONS:CONNECT` は要らない（§1.1）。**SD には保存しない**（起動したら OFF）。
- 受信モードでないときの `ON` は `PONS:LIVE,ERROR,NOT_RX`（受信機だけの機能。§4.5）。
- 止まる条件: `LIVE,OFF` / `PONS:CONNECT`（ファイルの一覧・取り出しとは同時にしない。§4.4）/ DTR が落ちた（ポートを閉じた・ケーブルを抜いた。`Serial` が false）/
  受信モードでなくなった。
- **無通信のタイムアウトは付けない。** PC 接続の画面は 60 秒で抜けるが、配信の途中で黙って止まるのが一番困る。書けないときは §1.2 で捨てるだけなので、
  読まれていなくても受信機は困らない。Re:PONS はつなぎ直したら `ON` をもう一度送る（何度送ってもよい）。
- log.txt に `LIVE ON` / `LIVE OFF (<理由>) lines=… dropped=…`。

### 4.2 書き方（止めない）
- 新しく `live.cpp` を作り、行のリングと `live_tick()` を置く。`loop()` の最上位で毎回呼び、`availableForWrite()` に収まる行だけ書く。
- 行を足すのは Core0 だけ（無線の受信も描き直しも Core0）。Core1 からは書かない（Core1 は SD と音で止まる）。
- **LIVE 中の Core0 のほかの返事（`PONS:TIME,OK` など）も、行をまるごと書く**ので、LIVE の行の間には挟まらない（§1.2）。
  RELEASE でないビルドの `DEBUG_P` は混ざる。Re:PONS は知らない行を捨てる。

### 4.3 どこで行を作るか
- `LT`: `link_poll_radio()` の `createSaveRxCsvTask()` の隣（`received/` に書く行と同じ瞬間・同じ値）。
- `LN`: ミラー中の地図は「フレームを受けた直後」だけ描き直す（`link_take_draw_frame()`。TFT のバスの雑音を受信に重ねないため）。
  その描き直しが終わったところで、画面に使った値を 1 行にする。**描く関数の中には書かない**（CLAUDE.md「描画に判断を混ぜない」）。
  値を集める関数を 1 つ作り、描き直しのあとで呼ぶ。
- `LS`: `loop()` の 1 秒ごとの tick。

### 4.4 PC 接続（ファイル一覧）とは同時にしない
- ファイルの転送中は、本体は転送以外を 1 行も書かない約束（pons_webserial_protocol.md §4 (3)）。`PONS:CONNECT` を受けたら LIVE を止める。
- Re:PONS の側は仕掛けを持たない。同じ USB のポートはブラウザが 1 つの窓にしか開かせないので、ライブの窓が開いている間は本体の窓の
  ファイルの接続が開けない（逆も同じ）。開けなかった側に「ほかの窓が使っている」と出る（2026-11-24。初めは BroadcastChannel で
  ボタンを押せなくしていたが、ブラウザがもう止めているので削った。§10.5）。

### 4.5 受信機だけ（2026-11-23 に決めた）
- **送信機・OFF のときは流さない。** `ON` は `NOT_RX` で断り、LIVE 中に受信モードでなくなったら `PONS:LIVE,OFF,MODE` で止める。
- 机の上の試験は送信機と受信機の 2 台が要る。Re:PONS の描き直しの開発は、2 台で一度とった行を保存して再生すれば 1 台も要らない（§5.7）。

### 4.6 受信機の画面の `LIVE` の印（2026-11-23 に決めた）
- 受信機の TFT に小さく `LIVE` を出す。ボートの人が、つながっているか・PC が読んでいるかを見るため。
  - 緑: 流している（直近 3 秒に行を書けた）
  - 赤: 行を捨てている（PC が読んでいない。Chrome が止まった・ケーブルは挿さっているがページを閉じた、など）
  - 出さない: LIVE を止めている
- 置き場所は電波のアイコンの近く（受信機の側の状態で、電波のアイコンと同じ種類）。機体の画面の項目に重ねない。正確な位置は作るときに決める。
- **描くのはふだんの描き直しの中だけ。** ミラー中の地図はフレームを受けた直後だけ描き直す（`link_take_draw_frame()`・`link_draw_window_ok()`。
  TFT のバスの雑音を受信に重ねないため）ので、印の色が変わったからといって別に描き直さない（変わるのは最大 1 秒遅れるだけ）。
- **Re:PONS の配信の画面には描かない**（受信機の側の印で、パイロットの画面には無い）。
- pons_link.md §5.1 の「ミラー中に自機の状態を混ぜない」の表に、例外として足す（電波のアイコンと同じ扱い）。

## 5. Re:PONS

### 5.1 つなぎ方
- ヘッダーに「📡 ライブ」のボタン（ファイルの接続とは別）。ポートを開いて `PONS:LIVE,ON` を送り、返事が来てから `PONS:TIME,<ms>`（今までどおり。起動中の受信機へ先に送ると時刻が古くなるため。2026-11-24）。
  **`PONS:CONNECT` は送らない。**
- `LIVE,OK` が 4 秒来なければ、「ファームが古い（LIVE を知らない）」か「受信モードでない」と出す。
- 切れたら（ケーブル・Mac のスリープ）自動でつなぎ直して `ON` を送り直す（配信中に人が触らなくてよいように）。
- Re:PONS を変えたら `VIEWER_VERSION` を上げる（CLAUDE.md）。
- ライブの部分は index.html に書き足さず、別の .js（例: `live.js`・`live_screen.js`）にして index.html の読む一覧の後ろに足す
  （2026-11-23 に index.html を分けた。CLAUDE.md の Re:PONS の約束）。Web Serial のつなぎ方は `serial.js` のものを使う。

### 5.2 読み取り
- `LT` の LinkTelem を `DataView`（リトルエンディアン、詰めた並び）で読む。並びは [link_proto.h](../lora_link/link_proto.h) の `LinkTelem`。
  **`LINK_PROTO_VER` と大きさが `LIVE,OK` の値と合わなければ描かない。**
- 試験: wire2_test（C）で LinkTelem を何通りか作り、16 進と値の JSON を書き出す。Re:PONS の読み取りを jsc で通して比べる
  （パイロン座標の見張りを jsc で確かめたのと同じやり方）。

### 5.3 画面の再現
- canvas に**論理 240×320**（本体と同じ座標）で描き、整数倍（×3 で 720×960、×4 で 960×1280）に拡大して出す。本体の座標・色（`COLOR_*`）・文字の大きさを写す。
- 描くもの（本体の地図画面）: ヘッダー（真方位 / 平均ピッチ / 推定 TAS の大きい枠・GS・高度）・地図（ベクター地図・目的地の線・航跡・機体のアイコン・距離の目盛り）・
  VSI のバー・姿勢・フッター（時刻・電池・衛星・精度）・コース警告・取消線と札。正確な一覧は作るときに display_tft.cpp から洗い出す。
- 描かないもの: **受信機の側だけのもの**（受信強度の数値・電波のアイコンの RX・受信機の充電ポップアップ・DUP SENDER の箱・`LIVE` の印）。
  配信の画面は機体の画面。ボートの側の情報は画面の外の帯に出す（§5.8）。**ボートの位置も地図に描かない**（パイロットの画面に無いもの）。
- 縮尺は**送信機の縮尺**（`scale_index`。2026-11-23 に決めた）。受信機は自分の縮尺を使う（pons_link.md §5.1）が、配信はパイロットの画面なので。
  届くまで（回転枠 6）は標準（画面幅 約 18km）。
- 地図の向き（`upward_mode`）は電波に載っていない。Re:PONS で選ぶ。既定は本体の既定と同じ track-up（パイロットが north-up にしているときだけ切り替える）。
- 航跡は、LIVE を始めてから受けた位置だけで描く（始める前の分は要らない。2026-11-23 に決めた）。Re:PONS をつなぎ直したときも、Re:PONS が持っている分は消さない。

### 5.4 地図（本体と同じベクター地図。2026-11-23 に決めた）
- `tools/vectormap/build_vectormap.py` に Re:PONS 用の書き出し（バイナリ）を足し、canvas に本体と同じ線・色・LOD の切り替えで描く。
  ネットが無くても描ける。Leaflet と地図タイルは使わない（見た目が本体と違う）。
- **本体と同じ版の地図を使う。** いまの本体は `VECTORMAP_HIRES`（settings.h）で、hires の元データから作る。light から作ると細かさが本体と違う。
- hires の生成物（`src/flashdata/vectormap_data_hires.cpp`）は git に入れていない。Re:PONS 用の書き出しも数 MB になる見込みなので、
  **置き場所は作るときに決める**（git に入れるか・公開ページにどう載せるか。スケッチのフォルダの中に置くとビルドのたびに写される＝CLAUDE.md）。
- OpenStreetMap 由来なので、帯（§5.8）に `© OpenStreetMap contributors` を出す（ODbL）。
- 段階 1（§8）は地図なし（数字と機体の点）で、データの道だけ確かめる。

### 5.5 動きの補間（する。2026-11-23 に決めた）
- そのまま描くと、地図と機体のアイコンが 1 秒ごとに跳ぶ（受信機の画面と同じ）。
- **1 発遅らせて、前のフレームと今のフレームの間を 1 発の間隔かけて動かす**（位置・地図の回転・姿勢の傾き）。**数字は補間しない**（届いた値だけを出す。作った数字を出さない）。
  配信はもともと数秒〜十数秒遅れるので、1 秒の遅れは見えない。
- 取りこぼし（受信率 70〜90% の距離）では、間が 2 秒以上になる。そのときは補間をやめて跳ばす（作った動きを長く見せない）。何秒で跳ばすかは作るときに決める（§10.2）。
- 補間のオン・オフを Re:PONS で選べるようにする（比べるため。既定はオン）。

### 5.6 途切れたとき
- `LS` が NO SIGNAL を言う（または `LT` が 3 秒来ない）なら、最後の画面を灰色にして `NO SIGNAL 12s` を重ねる。ボートの値に替えない（§1.3）。
- USB が切れたとき（`LS` も来ない）は `PONS 未接続` と分けて出す（受信が切れたのか、ケーブルなのかを分ける）。

### 5.7 記録と練習
- 受けた行を全部ファイルに保存できるようにする。SD の `received/` は判断の行と電波の生のバイトを持たないので、配信で何が出ていたかの記録になる。
- 保存したファイルを Re:PONS で**再生**できるようにする。受信機・送信機がなくても OBS の配置を練習でき、描き直しの開発にも使える
  （送信機では流さないので、2 台を出さずに開発できるのはこれだけ。§4.5）。

### 5.8 ボートの側の情報の帯（配信に出す。2026-11-23 に決めた）
- 機体の画面（240×320）の**外**、すぐ下に横長の帯を付け、同じ窓で 1 つのキャプチャにする（OBS で切り抜けば別々にも置ける）。
  機体の画面の中には混ぜない（§1.3。見た目は本体と同じ）。
- 出すもの（どれも `LS` の値。受信機が計算したもの）:
  - **受信強度**: 直近 10 秒の平均 dBm と本数（受信機の画面の数値と同じ）。
  - **機体までの距離**: ボートの位置から機体まで（`received/` の `dist_m` と同じ計算）。ボートが fix していないときは `--`。
  - 受信の状態: `NO SIGNAL 12s` / `PONS 未接続`（§5.6）。
  - `© OpenStreetMap contributors`（§5.4）。
- ボートの値だと分かる書き方にする（例 `BOAT RSSI` / `TO PLANE`）。機体の値と取り違えないため。文字の言葉・並び・大きさは作るときに決める（§10.2）。

## 8. 段階と確かめ方

1. **データの道**（ファーム: `LIVE,ON/OFF`・`LT`・`LS`・リング / Re:PONS: ライブの接続・LinkTelem の読み取り・数字の表・保存）
   - 机の上で送信機＋受信機＋ Mac。`LT` の値が受信機の画面・`received/` の CSV と同じか。
   - **受信機が止まらないこと**: Re:PONS の読み取りを止める（JS で読まない）・タブを閉じる・ケーブルを抜く、を繰り返して、受信機の 60 秒ログの
     `drain=` と `redraw` が LIVE なしと変わらないか、`received/` が欠けないか、`LIVE: dropped=` が増えるだけか。
   - USB をつないだだけで受信が悪くならないか（電池だけのときと受信率・RSSI を比べる。受信機は TFT のバスの雑音を避けているので、USB と Mac の雑音も見る）。
   - 受信機の `LIVE` の印: 読んでいる間は緑、Re:PONS の読み取りを止めると 3 秒ほどで赤、`LIVE,OFF` で消えるか。印を描いても受信率が落ちないか。
   - 送信機・OFF のときの `ON` が `NOT_RX` になるか、LIVE 中に受信モードから外すと `LIVE,OFF,MODE` で止まるか。
2. **画面の再現**（ファーム: `LN`・`DEST` / Re:PONS: canvas の地図画面・hires のベクター地図・送信機の縮尺・補間・ボートの帯）
   - 受信機の TFT と Re:PONS を並べて写真を撮り、数字・線・札が同じか（縮尺は受信機を送信機と同じにして比べる）。目的地を変える・Auto10km の折り返し・
     GROUND → 飛行の切り替え・送信機の電源を切る（NO SIGNAL）。
   - 送信機の TFT とも比べる（縮尺と地図の細かさが送信機と同じか）。
   - ボートの帯の受信強度・距離が受信機の画面・`received/` の `rssi` / `dist_m` と合うか。
3. **配信の仕上げ**（ポップアップ・OBS・背景・保存した行の再生）
   - OBS で 30 分以上流し続けて、取りこぼし・遅れ・Chrome の描画の止まりが無いか。

### 10.3 音（Re:PONS では鳴らさない。2026-11-24 に決めた）

### 10.6 帯に足した「送信機の目的地が受信機に無い」（2026-11-24、ユーザー）
- 受信機が送信機について確かめていること（縮尺・目的地・SD / IMU / 電源の異常・電池・`TIME?`・DUP SENDER・別グループ）のうち、
  帯に足したのはこれだけ。足す基準は「**配信の画面が、何の印も無くパイロットの画面と違ってしまう**」こと。
- 目的地は名前と座標の ID で照合するので、3 台の destinations.csv やパイロン座標の上書き（Re:PONS で変えられる）がそろっていないと、
  受信機は目的地を「未選択」にする。配信の画面からはパイロットの画面にある目的地の線・TC・距離が消える。受信機は `LS` の 0x08 で知らせ、
  Re:PONS は帯の下の段にオレンジで `PLANE DEST NOT IN BOAT PONS`（NO SIGNAL・DUP SENDER の次）。
- 足さなかったもの: 送信機の縮尺（配信の地図はもう送信機の縮尺で描いている。標準の縮尺かは飛ぶ前にパイロットが確かめる）/
  SD・電源の異常・電池（パイロットの画面の一部として描いている）/ IMU の異常・`TIME?`（ボートの人向け。受信機の WIRELESS 画面と音）/
  別グループ（NO SIGNAL のとき受信機の画面に `GROUP X FOUND`）/ 目的地が「違う」（受信機がすぐ送信機に合わせ直すので続かない。
  送信機は起動すると PLATHOME なので「未選択」も実際には起きない）。
- 地図の向き（トラックアップ / ノースアップ）も配信と食い違いうるが、電波に載っていない（変えるなら電波の形から）。Re:PONS で手で合わせる。
