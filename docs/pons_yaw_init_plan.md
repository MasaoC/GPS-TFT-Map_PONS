# ESKF 初期ヨー推定（発進加速の活用）— 問題提起と改善計画

> 2026-11-18 の調査・自転車走行ログ（`20261118.bin`）に基づく整理・提案メモ。未実装（計画段階）。

---

## 0. ひとことで

- 現在の ESKF は、発進時に **「`GS >= 3.0 m/s` を 4 回連続（1 秒間）満たした瞬間」に GNSS 航跡からヨーを注入し、`Y95% = 30°`（1σ = `15°`）で開始** する。
- この仕組みでは **加速の前半（0 → 約 4 m/s）がヨーの収束に一切使われない** ため、離陸時の「0 → 6 m/s（4 秒）の加速 1 回」だけでは `Y95%` が `29°` 程度までしか下がらず、そのまま一直線フライトに入ると **偏流点線（`10°` 未満）や 10° 基準のアイコン回転が出ないままになる** 問題が起きる。
- 対策の第一候補として、過去データを配列に溜めて遡るのではなく、**待機中〜発進中を通じて 6 個の `float` だけを前向きに更新し続ける「常時前向き 2D 回転相関」** による初期ヨー算出を提案・計画する。

## 1. 問題提起

### 1.1 現状の仕様（`settings.h` / `attitude.cpp`）

- ヨー未設定（`!yaw_set_`）の間は GNSS 速度観測を通さず、静止中の再水平化のみ動かす（ヨー誤差が大きいまま速度観測を入れるとロール・ピッチが壊れるため）。
- `sAcc <= ESKF_SACC_MAX`（`1.0 m/s`）かつ `GS >= ESKF_YAW_INIT_MIN_SPEED_MPS`（`3.0 m/s`）が `ESKF_YAW_INIT_ARM_FIXES`（`GNSS_NAV_RATE_HZ = 4` 回＝1.0 秒）連続した時点で、`init_yaw_from_track(trk, ESKF_YAW_INIT_SIGMA_DEG)` を呼び出す。
- 初期標準偏差は `ESKF_YAW_INIT_SIGMA_DEG = 15.0°`（すなわち **`Y95% = 30.0°`**）に固定されている。

### 1.2 離陸加速（0 → 6 m/s を 4 秒）でのシミュレーション結果

実機 C++ コード（`attitude.cpp`、250 Hz IMU / 4 Hz GNSS）そのものへ `0 → 6 m/s`（等加速度 `1.5 m/s²`・4 秒間）の直線加速を入力したシミュレーション結果は以下のとおり。

| パターン | GNSS `sAcc` | ヨー注入時刻（`30.0°` へ） | 4 秒（6 m/s）到達時 | 加速後の最小値 |
|---|---:|---:|---:|---:|
| 現行仕様（後半約 1.25 秒のみ使用） | 0.25 m/s | t = 2.75 s（4.13 m/s） | **29.27°** | **28.95°**（t = 5.25 s） |
| 現行仕様 | 0.50 m/s | t = 2.75 s（4.13 m/s） | **30.01°** | **29.89°**（t = 5.00 s） |
| 現行仕様 | 0.10 m/s | t = 2.75 s（4.13 m/s） | **24.89°** | **20.62°**（t = 8.00 s） |
| （参考）加速 4 秒全区間を観測に使用 | 0.25 m/s | — | 24.89° | **14.59°**（t = 6.00 s） |
| （参考）加速 4 秒全区間を観測に使用 | 0.10 m/s | — | 21.89° | **9.31°**（t = 6.00 s） |

#### 見えてきた課題
1. **加速前半の切り捨て**: `3.0 m/s × 4 回連続` を待つと、注入時点で既に `4.13 m/s` に達しており、残りの速度増分（`Δv ≈ 1.9 m/s`）だけでは GNSS 速度誤差（`sAcc`）に埋もれて `Y95%` がほぼ縮まない。
2. **強風時の低速リフトオフ（`GS ≈ 3 m/s`）＋横滑り発進への脆弱性**:
   - 向かい風が強い場合、対地速度 `GS = 3 m/s` 程度でリフトオフし、それ以上対地加速しないまま横風で横滑り（クラブ角・ドリフト）しながら飛ぶケースがある。
   - 現行仕様では浮揚して横滑りが始まった後の航跡 `trk`（機首から大きくズレた方向）を初期ヨーとして入れてしまい、しかもその後加速しないため直進中ずっと修正されない。
3. **直線加速の観測限界と初期 σ の固定（`15°`）**: 初期 σ を一律 `15°`（`Y95% = 30°`）に固定している限り、加速後に `10°` 未満へ届かない。`sAcc ≈ 0.1 m/s` の好条件と蓄積した加速エネルギーに応じた **動的初期 σ** が必要。
4. **発進加速中の重力観測（`level_update`）の誤発火（既存バグ）と最大 3.5° の下り・斜め勾配**:
   - プラットフォームや滑走路には最大 3.5° の下り勾配（斜め加速含む）がある。静止中は真の重力方向へ水平化されるため斜面自体は問題にならないが、現在の `attitude.cpp`（L1033）は `!yaw_set_` の間に `gnss_vel_fresh()` が `false` となるため前後加速度ゲートが効かず、**滑走加速中に 2 Hz の `level_update()` が発火して前方加速度を「傾き」と誤認し、水平基準 `q_` を狂わせる問題** がある。
   - **→ 2026-11-18 に直した（この計画とは別に先行して）。** 原因はもう 1 つあり、等加速度の滑走はジャイロが静かで `|a|` も g に近いので静止の判定を通り、
     待機中の維持（時定数 1 秒）も加速度の向きへ寄せていた（機上の `attitude.cpp` で 0→6 m/s を 4 秒の模擬、ピッチ 8.7°）。
     直し: 前後加速度の門の鮮度を測位で見る（`gsp_fresh()`。`eskf.py` はもともとこの形で、機上とずれていた）、
     「いまの推定で見た水平の比力 > 0.5 m/s² かつ 加速度計の値が直近の平均から 0.3 m/s² 以上変わった」間は加速中とみなし、
     待機中の維持・地上での維持・方位が決まる前の重力観測で寄せない（`settings.h` の `ESKF_ACCEL_*`、8 秒で解除）。
     `level_update()` を止める案は採らなかった（方位が決まる前に動かし続けたとき、傾きを支えるものが無くなるため）。
     模擬のピッチは 8.7° → 0.04°（`tools/attitude_test` の D5）。§1.2 の表の数字はこの直しと 11/18 の雑音の設定の変更の前のもの。

## 2. 実測ログの確認（2026-11-18 自転車テストほか）

2026-11-18 10:12〜10:28 の自転車走行データ（`imuraw/20261118.bin` Session 1・250 Hz / 4 Hz）および過去 CSV ログ（`2026-11-11〜18`）を解析して確認した事実：

1. **`sAcc` の実測値**: 自転車走行区間（`t >= 650 s`）の `sAcc` は **中央値 `0.086 m/s`、90% タイル `0.104 m/s`**（起動後十分落ち着けば約 0.1 m/s が得られる）。
2. **速度帯ごとの航跡誤差（対 ESKF 収束後ヨー）**:
   - このテストでは**意図的に約 10° ずらしてマウントした実験条件**（実測 `trk - eskf_yaw` 中央値 `-10.92°`）で行ったため、これを差し引いた純粋な航跡のばらつきを速度帯別に集計した（※実機本番ではまっすぐ固定される予定）。
   - `1.0〜2.0 m/s`: 1σ = `6.16°`（95% 誤差 `20.88°`）
   - `2.0〜3.0 m/s`: 1σ = `4.48°`（95% 誤差 `10.96°`）
   - `3.0〜4.0 m/s`: 1σ = `2.88°`（95% 誤差 `6.08°`）
   - `4.0〜10.0 m/s`: 1σ = `2.44°`（95% 誤差 `4.57°`）
   - **示唆**: `sAcc ≈ 0.1 m/s` でも `1〜2 m/s` 帯は車体のふらつき等で 95% 誤差が 20° 超あること、またプラットフォーム上の手押し運搬（1〜2 m/s）で誤注入を防ぐため、`ESKF_YAW_INIT_MIN_SPEED_MPS` を安易に `1 m/s` 台へ下げるのは危険。
3. **過去 CSV ログ全体の傾向**:
   - 一度大きな旋回が入ると `Y95%` は `3°〜5°` まで落ちて以後は `10°` 未満を維持する。
   - 一方、直進が続く初期区間（例：`2026-11-18_1001.csv` の発進後 60 秒間、`2026-11-14_1053.csv` の約 3 分間）は `10°〜20°` 帯に留まる。

### 3.1 検討した選択肢

### 3.2 常時前向き 2D 回転相関の仕組み

`!yaw_set_`（ヨー未設定）の間も、ロール・ピッチは静止水平化＋静止中再水平化によって正しく保たれているため、**「仮のヨー角のままの水平面内での IMU 加速度 `a_rel = (R * f_body)_{E,N}`」** は 250 Hz で測れている。必要なのは仮の ENU 座標系を真の ENU 座標系へ回す **1 つの水平回転角 `ψ`** だけである。

1. **IMU 側（250 Hz 更新）**: 水平比力を時定数 `τ`（例：`3.0 s`）でリーキー積分（指数ハイパス）する。
   ```text
   v_imu_hp = v_imu_hp * exp(-dt / τ) + a_rel * dt     // 2 floats (E, N)
   ```
   - リーキー積分により、静止中の微小な加速度バイアスがあっても無限に発散せず定常値 `ba * τ` で頭打ちになる。
2. **GNSS 側（4 Hz 更新、`sAcc <= ESKF_SACC_MAX`）**: 同じ時定数 `τ` の一次 LPF を引き、同条件のハイパス速度変化を作る。
   ```text
   v_gnss_lp += (1 - exp(-dt_g / τ)) * (v_gnss - v_gnss_lp)   // 2 floats (E, N)
   dv_gnss    = v_gnss - v_gnss_lp
   ```
   - 数学的に「IMU 比力の時定数 `τ` リーキー積分」と「速度の同一次ハイパス `v - v_lp`」は同一応答になるため、**`dv_gnss ≈ R_z(ψ) * v_imu_hp`** が常に成立する。
3. **2D 回転相関の逐次積算（4 Hz 更新）**: 内積 `C` と外積 `S` を指数減衰付きで更新する。
   ```text
   w   = 1 / max(sAcc, 0.05)^2
   dec = exp(-dt_g / τ_cs)      // 例: τ_cs = 4.0 s
   C   = dec * C + w * (v_imu_hp.e * dv_gnss.e + v_imu_hp.n * dv_gnss.n)
   S   = dec * S + w * (v_imu_hp.e * dv_gnss.n - v_imu_hp.n * dv_gnss.e)
   ```
   - この 2 スカラーから、任意の瞬間に **`ψ = atan2(S, C)`** で大域解（`±180°`、初期角ゼロ仮定なし）が直接求まる。
   - 必要な追加状態は **`v_imu_hp[2], v_gnss_lp[2], C, S` の `float` 6 個のみ**（O(1) 計算）。

## 4. 導入した場合に「なくせるもの」と「残るもの」

| 区分 | 項目 | 扱い・理由 |
|---|---|---|
| **置き換わる／簡素化できるもの** | `init_yaw_from_track()` による 1 点航跡の粗入れ替え | 2D 相関 `ψ = atan2(S, C)` による `rotate_world_z` に置き換え（または低エネルギー時のフォールバック専用に縮退） |
| | 固定 `ESKF_YAW_INIT_SIGMA_DEG = 15°` 一律代入 | 相関強度 `mag = hypot(C, S)`（蓄積した加速量×精度重み）に応じた合理的な初期 `σ` 算出が可能に |
| | `yaw_arm_`（4 回連続待ち）への強い依存 | 加速エネルギー `mag` が十分大きければ後半の待ちに頼りすぎずに済む（ただし誤注入防止の安全ゲートは別途必要） |
| **残る（なくせない）もの** | 初期水平化（`initialized_`・`init_level`）と静止再水平化 | 鉛直軸（重力方向）が正しくないと水平加速度 `a_rel` に重力漏れが混ざるため必須 |
| | ヨー未設定フラグ（`yaw_set_`）と発火ゲート | 静止中・運搬中に ESKF 本体の速度観測を通さないため、最小速度／最小 `mag` 等の門は必須 |
| | 異常回復系（`yaw_suspect_`, `relevel_big_tilt`, `imu_gap_recover`） | 大傾斜置き直し・IMU 途絶後の再検証用として存続（内部の初期ヨー入れ直しロジックは共用可能） |
| | GNSS 速度観測の通常 ESKF ループ（`P` 更新） | 一度 `yaw_set_ = true` になった後は従来どおり線形 ESKF が最適推定・バイアス推定を引き継ぐ |

## 5. 運用前提を踏まえたリスク・注意点と対策

### 5.1 最重点課題：プラットフォーム上の長時間微調整・手押し運搬での偽蓄積・誤発火

プラットフォーム上では、離陸前に**長時間にわたって機体を手で動かしたり、向きを変えたり、位置を微調整したりする可能性が高い**。運用側の注意で回避することはできないため、**コードのみで完全に防ぐ構造** にする必要がある。

- **想定されるリスク**:
  - 微調整・手押し（0.5〜2 m/s 程度）や風揺れ・振動が続く間に、ロール・ピッチの残留誤差（1° の傾き誤差 ≒ `0.17 m/s²` の偽水平加速度）や GNSS のふらつきが `v_imu_hp` / `C, S` に混入し、誤った値のままヨー確定（`yaw_set_ = true`）してしまう、あるいは離陸加速時の相関を汚す。
  - 一度プラットフォーム上で誤って `yaw_set_ = true` になると、その後の待機・向き変更のあいだ ESKF 本体の速度観測と地上維持が誤作動する。
- **コード上の多層防御（運用に頼らない対策）**:
  1. **確定ゲートには手押しでは絶対に超えない速度条件を残す**: 2D 相関が何を積算していても、ヨーを確定（`yaw_set_ = true`）させる条件には従来どおり `GS >= ESKF_YAW_INIT_MIN_SPEED_MPS`（`3.0 m/s`）の連続維持＋ `sAcc` 良好条件を課す。微調整・徒歩運搬（1〜2 m/s）では絶対に確定させない。
  2. **静止中（`static_now_`）のリセットと極低速時の `C, S` 積算停止**:
     - `static_now_` が一定時間（例：1〜2 秒）続いたら、`v_imu_hp`・`C`・`S` を明示的にゼロクリアする（微調整が終わって止まるたびに過去をリセット）。
     - 動いていても `GS < 0.8〜1.0 m/s` 程度（かつ `sAcc` 良好でない場合）は `C, S` へ積算しない。これにより停止中の GNSS ドリフトと傾き誤差の偽相関を構造的に防ぐ。
  3. **指数忘却（`τ ≈ 3 s`, `τ_cs ≈ 4 s`）**: 仮に離陸直前に微調整してすぐ発進した場合でも、数秒前の小さな手押し成分は指数減衰し、離陸時の強い加速（`1.5 m/s²`・4 秒）のエネルギーが圧倒的に支配する。
  4. **`mag`（相関強度）下限ガードとフォールバック**: 実機は本体を機体にまっすぐ固定する予定だが、強風時はリフトオフ直後から大きな偏流角（クラブ角）がつく可能性があるため、単なる航跡 `trk` との角度差だけで弾くのではなく、2D 相関の蓄積エネルギー `mag` が十分にあるかを主判定とし、`mag` が不十分な場合のみ従来の航跡 `trk` 注入（＋大きめ `σ`）へフォールバックする。

### 5.2 最大 3.5° の下り・斜め勾配および強風低速リフトオフへの対応

- **最大 3.5° の下り勾配・斜め加速と重力観測**:
  - 静止中の水平化（`init_level` / `level_toward_gravity`）は斜面の床ではなく **真の重力方向（真の水平面 ENU）** に合わせるため、発進前に数秒静止していれば 3.5° の斜面を斜めに加速しても水平成分 `a_rel` に重力は漏れない（斜面下向き成分 `-a sin 3.5°` は Z 軸にしか出ない）。
  - ただし、滑走加速中に 2 Hz の重力観測 `level_update()` が入ると、加速度ベクトルを重力と誤認して水平面 `q_` が傾いてしまう。対策として **`!yaw_set_` の間は `level_update()` を停止** し（静止中は 250 Hz の `level_toward_gravity` が担い、滑走中の数秒間はジャイロ積分で誤差 `< 0.1°` に保てる）、あわせて `level_update()` の前後加速度ゲートに `good_gnss_fresh()` と瞬時加速度ガードを追加する。
- **向かい風での低速リフトオフ（`GS ≈ 3 m/s`）＋横滑り発進**:
  - 2D 相関は「速度の向き＝機首」という運動学仮定ではなく **運動方程式（`dv_gnss / dt = R_z(ψ) * a_imu_hor`）** に基づくため、接地滑走中（`0 → 3 m/s`）の加速から機首方位を確定でき、浮揚後の横風ドリフト（クラブ角）や横滑り加速度に影響されない。
  - さらに、蓄積した情報量 `mag = hypot(C, S)`（`w = 1 / sAcc²`）から **動的初期 σ**（例：`σ_init = clamp(k / sqrt(mag), 3.5°, 15.0°)`）を設定することで、`sAcc ≈ 0.1 m/s` なら `0 → 3 m/s` の加速だけで注入直後から **`Y95% ≈ 8°〜9°`（`< 10°`）** となり、その後加速せず等速直進・横滑りに入っても即座にアイコン回転と点線を表示できる。
  - 強風で `GS` が `3.0 m/s` 付近で頭打ちになる場合に備え、`sAcc` が十分小さく `mag` が閾値を超えているときは連続待ち回数（`4 回` → `2 回` 等）や速度条件を緩和する設計とする。

### 5.3 実運用条件に照らして影響が軽微・対象外となる点

- **低加速度のじわっと発進**: 離陸時には必ず強い加速が入る運用であり、低加速度発進はありえないため、S/N 不足のリスクは限定的（念のため §5.1(4) の `mag` 下限フォールバックは入れておく）。
- **旋回しながらの発進における GNSS 遅延**: バンクは最大でも 8° 程度まで（`30 deg/s` のような急旋回率は出ない）であるため、GNSS 遅延（150 ms 程度）による加速方向と速度変化方向のズレは最大でも 1〜2° 以内に収まる。既存の `vhist_`（`ESKF_GNSS_VEL_DELAY_MS`）による時刻合わせで完全に対応できる。
- **本体の設置角度**: 11/18 の自転車テストでは意図的に約 10° ずらして試験したが、実機ではまっすぐ固定される予定であり、2D 相関が求める IMU 真方位はそのまま機首方位と一致する。

### 5.4 実装上のコスト

- **二重実装とテスト維持**: `CLAUDE.md` の方針により、`attitude.cpp` と `tools/imulog/eskf.py` は同一数式を保つ必要がある。定数（`τ`, `τ_cs`, `mag` 閾値など）と状態変数を増やす分、両者への同期実装と自動テストの整備が必要になる。
