# BNO085（i2c1）の手引き

対象: PONS v7 / 0.976 以降。

**0.976 で SPI 対応を削除し、i2c1 固定にした。**「触るとジャイロが化ける」現象
（触診で約 0.8 件/分、`gx=+v gy=-v gz=-v` の署名）が **SPI でしか起きず、I2C では
一度も再現しなかった**ため。SPI に戻す必要が出たら 0.975 の `imu.cpp` / `settings.h`。

この文書は 0.944（i2c0 + ブレイクアウト）との差と、v7 の i2c1 で踏んだ落とし穴の記録。

---

## 0. 前提 — 0.944 の「I2C で動いていた」は今とは別物

0.944 を根拠に「I2C なら動くはず」と考えないこと。**共通しているのは
`begin_I2C()` を呼ぶことだけ**で、ハードウェアもバスもアドレスの決め方も違う。

| | 0.944 | 現在 (0.975) |
|---|---|---|
| 実装 | GY-BNO080 ブレイクアウト | **v7 自作基板のベア IC** |
| バス | i2c0 `GPIO32/33` — **MS5611 と共用** | **i2c1 `GPIO34/35` — BNO085 専用** |
| クロック | 400kHz（`airdata_setup()` が設定済み） | 400kHz（`imu_setup()` が独立に `begin()`/`setClock()`） |
| アドレス | 0x4B（モジュール側で strap） | 0x4B（**MCU が `GPIO43`=SA0 を HIGH 駆動**） |
| プロトコル選択 | モジュール側で固定 | **PS1 = JP1 を GND、PS0 = `GPIO47` を LOW** |
| H_INTN | `IMU_INT_PIN -1`（未接続） | `GPIO45`。**I2C では読まない**（プルアップだけ入れる） |
| H_CSN | 無し | **基板上で未接続**（`R53` 外し。I2C では don't care） |
| 旧 SPI1 の SCK/MISO | 無し | **`GPIO42`/`GPIO44` が I2C バスとショート。`INPUT_PULLUP` で停める**（§4.2） |
| リトライ | `begin_I2C()` を 5 回（間に `delay(200)`） | **3 回。毎回 NRST を打ち直す** |

**バス分離の効果**: 0.944 は i2c0 を MS5611 と共用していたので、生レポートの
バス占有率（約 20%）が MS5611 の読み出しと競合していた。現在は i2c1 が専用なので、
**MS5611 のレートと BNO085 のレートは互いに影響しない**。

## 1. ソフトウェアの挙動の差（I2C 経路）

### 1.1 レポートの引き取り方が変わった

| | 0.944 | 現在 |
|---|---|---|
| 呼び出し | `imu_update()` が `sh2_service()` を **1 回** | `imu_service_if_due()` に集約 |
| 周期 | `IMU_POLL_INTERVAL_US` = 4ms | 同じ 4ms |
| 1 回の排出量 | 1 パケット | **最大 8 パケット**（`IMU_DRAIN_MAX_PACKETS`） |
| 呼ばれる場所 | `loop()` だけ | `loop()` ＋ **長いブロッキング処理の中から**（地図描画・E220 の待ち・起動画面の各待ち） |

`sh2_service()` は 1 回で 1 パケットしか処理しない（`shtp_service()` はループしない）。
0.944 は 4ms に 1 パケットしか掃けず、ブロックのあとで追いつけなかった。

**I2C 固有の打ち切り条件**: SPI は H_INTN で「まだ溜まっているか」が分かるが、
I2C では分からないので `_report_count == 0` で打ち切る。
→ **副作用**: advertisement やコマンド応答だけを処理した回はレポート数が 0 になるので、
まだ溜まっていても打ち切る。次の 4ms で拾うので実害は無いが、SPI と挙動が違う。

### 1.2 通信途絶の検出 — しきい値は同じ、ガードが増えた

しきい値は 0.944 も現在も **1 秒**（`imu_update()` 内）。
現在は手前に**呼び出し間隔のガード**がある:

> `imu_update()` の呼び出し間隔が 500ms 以上空いていたら、その回の判定を見送る。

これが無いと「データが来ない」と「こちらが見ていなかった」を区別できず、
**生きている BNO085 をリセットしに行って殺す**。2026-09-23 に SPI で実際に起きた。

### 1.3 復旧 — **0.944 の復旧も壊れていた。ただし一度も発火していなかった**

0.944 の `imu_try_recovery()` は NRST を打って `begin_I2C()` を呼び直すが、
`sh2_close()` を呼んでいない。取り込んだ SH-2 ドライバの SHTP インスタンスプールは
`MAX_INSTANCES=1` で空き判定が `pHal == 0`、それを 0 に戻すのは `shtp_close()` だけ。
**つまり 0.944 でも 2 回目の `begin_I2C()` は必ず失敗する。**

0.944 でこれが露見しなかったのは、`_last_sensor_event_ms` が
**`setup()` の間ずっと 0 のままだった**ため。途絶判定は
`_last_sensor_event_ms > 0` が条件なので、`loop()` の 1 回目では発火せず、
そこで初めてレポートが届いて時刻が入る。誤発報の入口が無かった。

現在は `sh2_close()` を `imu_bus_begin()` の冒頭で呼ぶので**復旧が実際に成功する**
（SPI で検証済み: `recovery OK (INT wait 12ms)`）。
I2C でも同じコードを通る。

| | 0.944 | 現在 |
|---|---|---|
| 形 | **ブロッキング**（NRST + 400ms で Core0 が 410ms 止まる） | 状態機械（`imu_reset_start()`/`imu_reset_poll()`。1 ループも止めない） |
| `sh2_close()` | **無し → 必ず失敗** | あり |
| 生存確認 | 無し | `begin_I2C()` の中の `detected()` が果たす（**自前で二重に探査しないこと**。§5.5） |
| 失敗ログ | `recovery FAILED` だけ | `FAILED (stage=N(no-ACK/no-SHTP) init_step=N sh2=N)` |

### 1.4 バスと初期化の順序（現在）

```
imu_bus_select_protocol()   PS0=LOW（プロトコル選択）/ SA0=GPIO43 を HIGH（0x4B）
                            H_INTN=GPIO45 と GPIO42/44 を INPUT_PULLUP（§4.2）
                            ★ GPIO41 は触らない（E220 の M0/M1 専用）
imuWire.begin() / setClock(400k)
imu_reset_blocking()        NRST を LOW→HIGH、ブート 400ms 待ち
[3 回まで] begin_I2C() → 失敗ならバス復旧 + NRST を打ち直して再試行
imu_enable_reports()        レート設定は settings.h に一元化
sh2_getCalConfig / setCalConfig(ACCEL|GYRO|MAG)
```

**PS1/PS0 はリセット時にラッチされる**ので、この順序を崩さないこと。

### 1.5 バスに関係なく変わったもの（I2C でも効く）

- **クォータニオンの健全性チェック** `quat_sane()`: `|q|²` が 1±0.02 を外れた GRV/RV を
  採用しない。カウンタは `quat grvbad= grvjump= rvbad=`。
  `grvjump` は**捨てずに数えるだけ**（速い手振りでも起こるため）。
- **校正設定**: `sh2_setCalConfig(ACCEL|GYRO|MAG)` を起動時に揃える。
  0.944 は触っていなかった（`calcfg=0x05`＝mag のみ＋accel のまま）。
  ログは `cal cfg=0x07 acc= gyr= mag=`。
- **DCD 保存**: 起動から 20 秒経過し精度 3 に達したとき 1 回だけ `sh2_saveDcdAndReset()`。
- **マウント補正**: 0.944 は Euler の組み替え（`display_roll = sensor_pitch` 等）。
  現在は**クォータニオン回転** `IMU_MOUNT_Q*`。v7 は IC が基板裏面・1 番ピンが天で、
  機体水平時にセンサーがジンバルロックに入るため、Euler では原理的に直らない。
  **この 4 つの値は v7 基板で実測したもので、SPI/I2C で共通。**
- **ESKF**: ヨー分散に上限（1σ=180 度）、自動ロールトリムに GNSS 速度の鮮度ゲート。

## 2. 取り込みライブラリの改変 — I2C への影響

`src/bno08x/PONS_VENDORING.md` の一覧を I2C の観点で読み替えたもの。

| 改変 | I2C への影響 |
|---|---|
| (1) `spihal_wait_for_int()` の待ちの粒度 | **0.976 で上流へ戻した**（SPI HAL のみで死んでいたため） |
| (2) `pons_pkt_max` / `toobig` / `hdr_change` カウンタ | **0.976 で撤去**（`spihal_read()` の中だけで、i2c1 では常に 0 だった） |
| (3) `sh2_hal.h` の受信バッファ 384 → 768 | **効く。** `shtp.c` の `inPayload[]`/`inTransfer[]` は共有。RAM +768B |
| (4) `pons_init_fail_step` / `pons_init_fail_status` | **効く。** `_init()` のどこで落ちたかが分かる |
| (5) `sh2_close()`（PONS 側の回避） | **効く。** これが無いと復旧が必ず失敗する |

> ### ★ 60 秒ログの `spi pktmax=...` は 0.976 で削除した
> あれは `spihal_read()` でしか更新されず、i2c1 では常に 0 だった。
> 「0 だから健全」と誤読されるだけなので外し、`imu gapmax=` だけ残した。
> I2C で同じことを知りたければ `i2chal_read()` にカウンタを足す必要がある。

> ### ★ `packet_size > len` の取りこぼしは I2C にもある
> `i2chal_read()` も上流のまま `return 0` で**パケットを排出せずに諦める**。
> バッファを 768 に広げて当たりにくくしただけで、構造は残っている。
> ただし I2C では INT を見ずにポーリングしているので、詰まると
> `_report_count == 0` が続いて 1 秒で途絶判定 → 復旧（今は成功する）に入る。
> **I2C ではカウンタが無いので、症状は「時々 recovery が走る」としてしか見えない。**

## 3. 標準の Adafruit ライブラリに戻したらどうなるか（I2C）

### 3.1 まずビルドが通らない（2 箇所）

| 箇所 | 参照しているもの |
|---|---|
| `imu.cpp` `imu_bus_begin()` | `pons_init_fail_step`（`sh2_close()` の要否判定に**使っている**） |
| ~~`GPS_TFT_map.ino` の 60 秒ログ~~ | 0.976 で `pons_pkt_*` の参照を削除したので、もう問題にならない |

前者は単なるログ用ではない。`sh2_open()` まで通って `getProdIds()` で落ちた場合も
SHTP インスタンスは取られているので、そこを区別しないと次回 `sh2_close()` を
呼び忘れる。**消すなら代わりの判定を用意すること。**

### 3.2 受信バッファが 384 に戻る

`i2chal_read()` は `packet_size > len` で捨てる。SPI で実測した最大パケットは
**276 バイト**（`pktmax=276`。同じレポート構成なら SHTP パケットは I2C でも同じ）。
384 でも即座に破綻はしないが余裕が 108 バイトしかない。
レートを上げる・レポートを増やすと当たりに近づく。

### 3.3 残るもの / 戻るもの

- **`sh2_close()` の復旧修正は `imu.cpp` 側なので残る。** ライブラリを戻しても復旧は動く。
- `spihal_wait_for_int()` のレート低下対策は SPI 専用なので I2C には関係ない。

### 3.4 include の書き方に注意

`imu.cpp` は `#include "src/bno08x/Adafruit_BNO08x.h"` と**相対パス**で書いてある。
`<Adafruit_BNO08x.h>` と山括弧に戻すと、インストール済みのライブラリを拾い、
**ローカル改変が効かないまま静かにビルドが通る**（CLAUDE.md）。
戻すなら意図して戻すこと。

## 4. I2C でテストする前のチェックリスト

### 4.1 ハードウェア

- [ ] **JP1（PS1）を 2-3（GND）へ**。1-2（+3V3）から変更する。
      ★ **I2C は PS1=0。HIGH ではない。** 取り違えるとラッチされて起動しない。
- [ ] **R46 / R47（0Ω）を実装**して H_SCL / H_SDA を i2c1（`GPIO34/35`）へ繋ぐ。
- [x] **i2c1 の外部プルアップ 4.7kΩ（`GPIO34/35`）** — 実装済み（2026-09-27 確認）。
- [x] **`R53` は外してある** → `GPIO41` は H_CSN と切れ、**E220 の M0/M1 専用**。
      BNO085 の H_CSN は基板上で未接続（I2C では don't care）。

### 4.2 ソフトウェア（すでに入っている。確認だけ）

- [x] **`GPIO42` / `GPIO44` を `INPUT_PULLUP` で停める**（`imu_bus_park_unused_pins()`）。
      **High-Z のまま放置してはいけない。** R46/R47 で H_SCL/H_SDA に繋がっており
      `GPIO34/35` とショートしているので、RP2350 のパッドが Low 側へ張り付くと
      外部 4.7kΩ と分圧して約 2.1V（VIH 2.31V 未満）＝ **Low に見えてバスが死ぬ**。
      実機 2026-09-27: `stage=2(no-SHTP) SDA=0 SCL=0` で 5 回中 4 回起動失敗。
      **出力にすると I2C バスを殺すので、出力にはしないこと。**
- [x] **`GPIO41` に触らない**（E220 の M0/M1 専用）。0.975 まで
      `imu_bus_select_protocol()` が HIGH 駆動しており、**無線を mode 3 へ
      叩き落としていた**（IMU 復旧からも呼ばれるので飛行中に効く）。
- [ ] `IMU_I2C_ADDR 0x4B` と `IMU_I2C_SA0_PIN 43` の整合（SA0=HIGH → 0x4B）。
- [ ] **バスが固まったら NRST だけでは戻らない。** `imu_i2c_bus_recover()` を
      リトライの **NRST より先に**通すこと（ペリフェラルを外して SCL を 9 回叩き
      STOP を作る）。RP2350 の I2C ブロックは NRST では初期化されないため、
      入れていないと **3 回のリトライが全部同じ理由で失敗する**。

### 4.3 焼いた直後に見るログ

| 行 | 読み方 |
|---|---|
| `BNO085 begin FAILED (i2c1) stage=1(no-ACK) SDA=.. SCL=.. addr=0x4B` | **アドレスが応答しない。**JP1(PS1) / R46・R47 / 3V3 / NRST / 半田を疑う。バスの波形以前の問題 |
| `... stage=2(no-SHTP)` | ACK は返る＝チップは居て I2C モードにいる。SHTP が成立しない（クロック・プルアップ・ノイズ） |
| `BNO085 init OK` + `calcfg=0x07` | 正常。校正設定も揃った |
| `rate GRV=15 LACC=15 RV=5 MS5611=44` | 設定どおり。**落ちていたら飢餓**（`gapmax` を見る） |
| `BNO085 i2c bus recover -> SDA=1 SCL=1` | リトライで出る。**0 のままならバスが解けていない** |
| `imu gapmax=` | BNO085 を引き取れた最長間隔。数十 ms 以内であること |
| `quat grvbad= grvjump= rvbad=` | **今回のテストの主目的**。触ったときに増えるかを見る |
| `[IMU] BNO085 recovery OK/FAILED (stage=..)` | 途絶が起きたときだけ。`stage=1(no-ACK)` なら配線 |

### 4.4 テストの主目的

**基板に触れた（ボタンを押さなくても、皮膚が接触して角度が変わるだけで）ときの
ジャイロのスパイク（SPI で約 0.8 件/分）が I2C で消えるか。**

**結果（2026-09-27）: I2C では一度も再現しなかった**ので、I2C 運用に確定した。
`quat grvbad=0 grvjump=0 rvbad=0` が続き、SPI で見えていたスパイクは消えた。

- 判定材料: `quat grvbad` / `grvjump`、バリオ設定画面の Linear acceleration の暴れ、
  生ログ（`imuraw/*.bin`）を `tools/imulog/decode_imulog.py` で確認
- 比較のため、**SPI のときと同じ持ち方・同じ触り方で同じ時間**測ること
- 消えなかった場合、容量結合ではなく IC か実装（はんだ・デカップリング）側の疑いが濃くなる

## 5. 加速度計の校正（バスとは無関係。ただし v7 実機で実際に出た）

### 症状

Vario 詳細画面で **`LinAccel[body]` は 3 軸ほぼ 0 なのに `VertAccel` だけ −1.5 付近**に落ち着く。
ロール・ピッチは正しく 0 を指しているので、姿勢の問題には見えない。

### 原因 — 引いている重力が違うだけ

| 表示 | 引いている重力 |
|---|---|
| `LinAccel[body]` | BNO085 の `LINEAR_ACCELERATION`。**BNO085 自身の適応的な重力推定**を引いた値 |
| `VertAccel` | 生比力を世界座標へ回して **固定値 `GRAVITY_MPS2` = 9.80665** を引いた値 |

加速度計にスケール／バイアス誤差があると、**前者は誤差ごと引いて打ち消す**ので静止時に
きれいに 0 になり、**後者は誤差がそのまま残る**。

実測（`nofix008`、静止 184 窓の平均。2026-09-27）:

```
|a|                          = 8.2243 m/s^2   ← 本来 9.807。加速度計が低く出ている
|LinAccel|                   = 0.0585         ← ほぼ 0
BNO085 が引いた重力の大きさ  = 8.2219
8.2219 - 9.80665             = -1.5848        = VertAccel の実測値
```

**`LinAccel` ≒ 0 は「加速度計が正常」の証拠にならない。**
構造上、静止時のスケール／バイアス誤差を打ち消すので見えない。
**`VertAccel` のほうが診断に使える。**

### 校正ずれの実測（nofix004 + nofix005、静止 7011 サンプル）

静止時の `|a|` は姿勢に関係なく常に 9.807 でなければならないが、実測は

```
|a| の範囲  8.094 .. 10.862 m/s^2   → 広がり 2.77 m/s^2
```

楕円体（対角スケール＋オフセット）のあてはめ（残差 1.0000 ± 0.0008）:

| 軸 | オフセット | スケール誤差 |
|---|---|---|
| **X** | **+1.31 m/s²** | −2.7% |
| Y | +0.28 | **判定不能**（下記） |
| Z | +0.01 | +3.2% |

水平では重力がセンサー −X を向くので、**X の +1.31 のバイアスがほぼ丸ごと出る**。
予測 −9.807×0.973 + 1.31 = −8.23 に対し実測 −8.09〜−8.28 で一致。

> **Y 軸の数字は信用しないこと。** そのログでは Y の範囲が −0.89〜+1.08 しかなく、
> **重力が Y 方向を向いた姿勢が一度も無い**。観測情報が無いのにあてはめは数字を返す。

### 直し方

1. `cal acc=` を 60 秒ログで見る。**3 になっていなければ校正が終わっていない。**
2. 基板を**各軸が上下を向く 6 姿勢**で数秒ずつ静止させる。**Y 軸を忘れないこと**
   （上の実測でも Y だけデータが無かった）。
3. `acc` が 3 に達すると `imu_try_save_dcd()` が 1 回だけ不揮発へ保存する
   （条件: 起動 20 秒以降 かつ `_acc_accuracy >= 3`）。
4. それでも 3 に届かないなら、過去の悪い校正データが残っている疑い。
   ドライバに `sh2_clearDcdAndReset()`（`src/bno08x/sh2.h`）がある。
   **呼び出しコードは未実装。**

### バリオへの影響

バリオ KF は状態にバイアス項 `kf_x[2]` を持つので、**一定のオフセットは吸収される**。
ただし今回の誤差は**姿勢で変わる**（水平 −1.6 / 機首下げ 82 度 +0.05 / 別姿勢 +0.41）ので、
ピッチやバンクが変わる場面では吸収しきれない。**精度の上限がここで決まる。**

### 5.5 ★ アドレス探査を二重にしてはいけない（0.976 で踏んだ）

**症状**: 起動が 5 回中 4〜5 回失敗する。

```
BNO085 begin FAILED (i2c1) stage=2(no-SHTP) init_step=1 sh2=0 SDA=0 SCL=0 addr=0x4B
```

**原因**: `imu_bus_begin()` が `begin_I2C()` の前に自前でアドレス ACK を確認していた。

arduino-pico の **0 バイト書き込みは I2C ペリフェラルを使わない**。ピンを SIO に
切り替えて**ビットバンギングで叩く**（`Wire.cpp` の `_probe()`）。そのビット幅は

```
delay = (1000000 / _clkHz) / 2      → 400kHz なら 1µs、100kHz なら 5µs
```

そして `begin_I2C()` → `Adafruit_I2CDevice::begin()` → `detected()` が
**まったく同じ `_probe()` をもう一度**叩く（間の `_wire->begin()` は
`if (_running) return;` で何もしない）。

結果、**同じビットバンギング探査が背中合わせで 2 回**走り、
**1 回目は通って 2 回目が落ちる**という形で毎回失敗していた。

**対処**: 自前の探査を削除した。**保護は `detected()` 自身が果たす**（`_init()` へ
進む前に false を返すので `sh2_getProdIds()` には到達しない）。

`IMU_I2C_HZ` は **400kHz のまま**でよい（真因は二重探査だった）。
**再発したときは、まずこれを 100000 に下げて切り分ける**（ビット幅が 1µs → 5µs）。

> 外部プルアップ 4.7kΩ は実装済みなので、**立ち上がり時間の問題ではない。**
> 探査がペリフェラルを使わずビットバンギングしている側の問題。

## 6. SPI へ戻す場合（非推奨）

0.976 で SPI のコードは削除した。戻すなら 0.975 の `imu.cpp` / `settings.h` /
`e220.h` / `src/bno08x/Adafruit_BNO08x.cpp` を見ること。ハード側は
**JP1 を 1-2（+3V3）へ戻す**。`E220_MODE_PIN` が `GPIO41` から動かせないため、
**`R53` を戻して H_CSN を繋ぐと E220 と衝突する**点に注意。
そして何より、**触るとジャイロが化ける問題が戻る。**
