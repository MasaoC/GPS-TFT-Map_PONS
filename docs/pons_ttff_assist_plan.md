## 0. ひとことで

- GNSS の時計の電池（BT1）が切れて起動すると、コールドスタートになる。小さいアンテナでは
  データシートの 23 秒ではとても済まず、**数分、車内など場所が悪いと 10 分以上**かかる（実機の体感）。
- 2 つの手を組み合わせる。
  1. **SD に GNSS の航法データベース（DBD）を置いておき、起動したら GNSS へ戻す**（無線を使わない）。
  2. **時刻を持つ仲間（機体・ボート）から LoRa で時刻をもらい、GNSS へ入れる**（UBX-MGA-INI-TIME_UTC。2026-11-13 に時刻だけと決めて実装。§4）。
     PC につないでいれば、PC の時刻も同じように入れる（§3.6。2026-11-10〜）。
- 予測軌道（AssistNow Autonomous。以下 ANA）を使うには、GNSS が**大まかな絶対時刻**を知っている必要がある
  （§2.2）。BT1 が切れると時刻も消える。ただし時刻は 1 衛星から読めるので、エフェメリスよりずっと早く手に入る。
  **1 は単独でも、GNSS が時刻を読んだところから効く見込み**（§3.4。DBD が新しいときだけ）。2 があれば最初から効く。
- **BT1 が生きている起動では何もしない**。そのときは GNSS の BBR に全部残っていて、ホットスタートに近い。

## 1. 守ること

### 1.1 ルール
- 大会のルールは「**上りの通信路で操縦しない（ラジコン禁止）**」。上りの通信そのものは禁止されていない
  （2026-11-08 確認。CLAUDE.md・pons_link.md も直した）。

### 1.2 PONS 本来の役割（下りのテレメトリと航法）に影響させない
- 上りで変えられるのは「**起動後に 1 回、GNSS へ時刻のヒントを入れる**」ことだけ。
  機体の操作・設定・表示・航法は、上りからはいっさい変えられない。
- **機体の 1Hz の送信は、タイミングも中身も変えない。** 足すのは status の空きビット 1 つ（§4.3）だけ。
- ビーコンは**テレメトリと別の印**にして、**別の読み取り口**で読む。ミラー表示・`NO SIGNAL`・`DUP SENDER`・
  `GROUP X FOUND` の判定には混ぜない。
- **2 発続けて食い違わないビーコンだけ**を使う。使うのは起動ごとに 1 回、最初の fix の前だけ。
- ボートが送るのは**頼まれたときだけ**。送るのは機体のテレメトリの合間だけ（§4.5）。
- `settings.txt` の `link_assist:OFF` で、受信の窓・要求・提供・DBD の保存と復元を全部止められる。
- リプレイ中・デモ中（`link_rf_suppressed()`）は送らない、使わない。
- **GNSS の UART を長く塞がない。** DBD の吸い出しは飛行中にやらない（§3.2）。
- SD を触るのは Core1 だけ（タスクキュー経由）。Core0 は待たない。

## 2. 調べてわかったこと

### 2.1 SAM-M10Q の数字（データシート UBX-22013293 R05）
| 項目 | 値 |
|---|---|
| ファームウェア | **ROM SPG 5.10**。SPG 5.30 は外部フラッシュか、起動のたびに RAM へ書き込む版なので、いまの基板では関係ない |
| TTFF（全衛星 −130dBm の条件） | コールド 23s、ホット 1s、AssistNow Online 1s、Offline 2s、**ANA 4s（2 日前のデータ）** |
| 感度 | コールド −146dBm、ホット −157dBm（**11dB の差**） |
| 電流 | 捕捉中 平均 13mA、追尾中 10mA、V_BCKP 28µA |

### 2.2 コールドが長い理由と、DBD が効く理由（Integration Manual UBX-22020019 R02）
- コールドでは衛星ごとにエフェメリスを読む必要がある（強い電波でも 18〜36 秒）。
  弱いと途中で 1 ビット誤るたびに次の周回を待つことになり、数分、10 分以上かかる。
- 弱い電波ではエフェメリスがまったく読めず、**ANA か A-GNSS が無いと fix できないこともある**、と明記されている（§3.11.4.3）。
  なので、データシートの差（23 秒→4 秒）以上に効く可能性がある。
- **ANA の予測軌道を使うには、RTC か外部からの時刻で、大まかな絶対時刻が要る**（§3.11.4.3）。
- バックアップ電池が無い場合について、IM §3.11.4 に次の記述がある。
  - UBX-MGA-DBD で ANA のデータを吸い出して保存できる。
  - ただし、予測軌道を計算するには絶対時刻（日付と時刻）が要る。
  - なので、UBX-MGA-INI-TIME_UTC で時刻を入れることを勧める。
- 通信で送った時刻は精度が悪い（§3.9.2）。ただし、ヒントには秒の単位で足りる。

### 2.3 Interface Description（M10 SPG 5.10、UBX-21035062 R03）で確かめたこと
| メッセージ | 要点 |
|---|---|
| **UBX-MGA-DBD**（0x13 0x80）§3.13.4 | ペイロードが空のポールを送ると、データベースを全部吐き出す。続けて UBX-MGA-ACK が来て、その `msgPayloadStart`（U4）が吐き出した DBD の数になる。1 通は最大 172 バイト（ペイロード 164）。**中身はファームウェアごとに違い、作った受信機へ戻す前提**（別の受信機には戻さない） |
| **UBX-MGA-ACK**（0x13 0x60）§3.13.1 | `CFG-NAVSPG-ACKAIDING`（0x10110025、既定 0）を 1 にすると、入れたデータ 1 通ごとに返事が来る。`type` は 1 なら使った、0 なら使わなかった。使わなかったときは `infoCode` に理由が入る。**`infoCode`=1 は「時刻を知らないので使えない。先に MGA-INI-TIME_UTC を入れよ」**。5 は「まだ受け取れない」 |
| **UBX-MGA-INI-TIME_UTC**（0x13 0x40、24B）§3.13.9.3 | `type`=0x10。`ref.source`=0 は「受け取った瞬間（不正確）」。`leapSecs`=−128 は「不明」。`tAccS`/`tAccNs` で精度を書く。**書いた精度より外れていると性能がかなり落ちる** |
| **UBX-MGA-INI-POS_LLH**（0x13 0x40、20B）§3.13.9.2 | `type`=0x01。高さは cm 単位、`posAcc` は cm 単位の標準偏差。**こちらも、書いた精度より外れていると性能がかなり落ちる** |
| **UBX-NAV-ORB**（0x01 0x34）§3.15.7 | 衛星ごとに、エフェメリス・アルマナック・予測軌道が**あと何分・何日使えるか**と、その出どころがわかる。エフェメリスは 15 分刻みで 450 分まで、アルマナックと予測軌道は 1 日刻みで 30 日まで。**DBD を戻した直後に読めば、効いているかが実機でわかる** |
| **UBX-NAV-SAT**（0x01 0x35）§3.15.13 | 衛星ごとの `orbitSource`（1 エフェメリス、2 アルマナック、3 Offline、4 ANA）と `svUsed`。**最初の fix にどの軌道が使われたか**がわかる |
| **UBX-NAV-AOPSTATUS**（0x01 0x60） | ANA が計算中かどうか。IM は「止まっているときに電源を切れ」と言う。吸い出しもこのときにする |
| **UBX-SEC-UNIQID**（0x27 0x03）§3.17.1 | GNSS チップの固有 ID。DBD のファイルをこの受信機に結びつけるのに使う |
| **UBX-CFG-RST** の `navBbrMask` | 0xFFFF でコールド（BT1 が切れたのと同じ）、0x0000 でホット。ビット 15 は ANA のデータ、ビット 8 は RTC。`resetMode`=0x02 は GNSS だけの再起動 |
| **CFG-ANA**（§4.9.1） | `USE_ANA`（0x10230001、既定 0。PONS は `GNSS_USE_ANA` で 1 にしている）、`ORBMAXERR`（0x30230002、既定 100m、5〜1000m。予測軌道の誤差をどこまで許すか） |

### 2.4 データがもつ期間
| 古さ | 使えるもの | 起動のしかた |
|---|---|---|
| 約 4 時間まで | 放送エフェメリス | ホットに近い（1 秒） |
| 約 3 日まで | ANA の予測軌道 | 数秒（データシートは 2 日前のデータで 4 秒） |
| 数週間まで | アルマナック | ウォーム（見える衛星はわかるが、エフェメリスは読み直し） |
| それより古い | なし | コールド |

- ANA の予測軌道は、何度も観測すれば最大 6 日まで延びる。ただし IM にはそのためにフラッシュが要るとあり、SAM-M10Q には無いので、**3 日と見る**。
- `ORBMAXERR` を大きくすると延びるが、精度と引き換え。
- DBD にアルマナックまで入るかどうかは、資料に書いていない（中身はファームウェアごと）。NAV-ORB で確かめる。
- 通電中は 30 分ごとに SD を書き直す（§3.2）ので、**2〜3 日おきに使っていれば SD の中身はいつも有効**。

### 2.5 SPG 5.10 の既知の制限（SPG 5.30 リリースノート UBXDOC-304424225-20393）
- **ANA を有効にしていると、コールドスタートのあと QZSS を航法に使わない**（5.30 で直った）。
  原文（§5 の "SPG 5.10 limitation"）: "After a coldstart QZSS satellites will not be used for navigation if AssistNow Autonomous is enabled."
  回避策は ANA を無効にすること。日本では、空の悪い場所で頼りになる高仰角の衛星が減る。
- **→ 2026-11-13 から、BT1 が切れていた起動（コールドスタート）だけ、その起動の間 ANA を切る**（v7.1・v7 とも。ユーザーの判断）。
  既定（`GNSS_USE_ANA` = 1）は有効のまま。条件はコールドスタートだけなので、BT1 が生きている普段の起動には当たらない。
  BT1 の生死は最初の NAV-PVT で分かるので、起動時の CFG-ANA はそのあとに送る（gnss.cpp の `gnss_ana_boot_tick()`）。
  - 同じ日に一度は全部の起動で切った（11/12 に取り出した log.txt で ANA がはっきり効いていなかったのと、体感で遅くなった気がしていたため）が、
    原文の条件を読んで戻した。11 回のうちコールドは 1 回だけで、遅かった 262 秒の起動は BT1 が生きていた（§7 の 0.a）。
  - **引き換え**: コールドの起動では SD の DBD に入っている ANA の予測を使わないので、DBD がはっきり効くのは保存から約 4 時間以内
    （エフェメリスの寿命）になる。§3.4 の「約 3 日」は ANA を使う前提の数字。またその起動の間は予測を作らないので、
    次の起動（BT1 は充電されて生きている）は最後の受信から 4 時間を過ぎると予測が無い。
  - QZSS が本当に使われるようになったかは log.txt で見る（まだ実機で確かめていない）: `GNSS ANA off for this boot (...): ack`、
    `GNSS QZSS first used Ns after boot (Qn of m seen, ana=off(cold))`、10 分ごとの `GNSS SVS used G.. E.. B.. Q.. R.. (QZSS seen n) ana=...`、
    `GNSS ORBIT after 1st fix: ... used G.. Q.. (QZSS seen n) ana=...`。
  - 机の上の `PONS:DBD,COLD` / `COLDONLY` は GNSS だけをコールドにする。2026-11-13 までは ANA がその起動で決めたまま（BT1 が生きていた起動なら有効）で、
    本物のコールドの起動（ANA 無効）と条件が違った。**2026-11-14 から、リセットの前にその起動の間 ANA を切る**（`gnss_ana_off_for_cold_test()`）。
  - **2026-11-13 の log.txt では、ANA が有効な普段の起動で QZSS がほとんど受かっていなかった**（屋外は車の中の 6 本だけで `QZSS seen` 0〜1、
    同じ車の v7 は 6。BeiDou も B0。ほかの 17 本は屋内で当てにならない）。「受かっているのに使わない」（上の制限）ではなく追っていないので、GNSS の設定（CFG-SIGNAL）で切られている疑いがある。
    → 同じ日に、起動時に CFG-SIGNAL を RAM・BBR・Default の 3 層で読んで log.txt に出し（`GNSS SIGNAL ...`）、BeiDou（B1I）・QZSS（L1C/A）が
    0 なら RAM に 1 を書くようにした（gnss.cpp の `gnss_sig_tick()`。v7.1・v7 とも・実機未確認）。CFG-SIGNAL を変えると GNSS が測位をやり直すので、
    ANA の設定・DBD の戻し・外からの時刻入れは `gnss_signal_cfg_settled()` を待つ。
  - 読んでみると、3 枚の GNSS 基板とも設定は工場出荷のまま全部有効だった（BeiDou は B1C のみ）。QZSS が見えないのは基板 b（`B386598FAF54`。v7.1 で使い続ける）について行った。
    **2026-11-14 から BeiDou を B1I にした**（`GNSS_BDS_B1I`。B1I は B1C・GLONASS と同時に有効にできないので GLONASS は使わない）。
    保存した DBD に GLONASS の分が入っていても、戻すときに GNSS が使わないだけ（`other` に数えられうる）。
  - **2026-11-14 に全ログを見直すと、QZSS はどの GNSS 基板でも一度も測位に使われていなかった**（受けているのは最大 6 機）。理由を見るため、
    QZSS の衛星ごとの health・orbitSource・放送暦／アルマナックの有無・qualityInd を log.txt に出すようにした（`GNSS QZSS (...): J..`。読み方は TODO メモ §5）。

### 2.6 E220 まわり
- M0/M1 は 1 本の GPIO（v7・v7.1 とも）。mode 0（受信待機 約 8.2mA）と mode 3（スリープ 約 2µA）しか無く、**WOR は使えない**。
  受信したい間は mode 0 で居続けるしかない。
- 送信時間は SF8・32 バイトで 70ms、モジュールが塞がる時間（AUX Low）は約 105ms（pons_link.md §3.1）。
- **E220 のキャリアセンス（ARIB）は、かぶりを防ぐ役に立たない**（§4.5）。

## 3. 手 1: SD に DBD を置く（段階 1。無線を使わない）

### 3.1 吸い出しと戻しかた
- **吸い出し**
  1. UBX-MGA-DBD のポールを送る。
  2. 返ってくる MGA-DBD を順に RAM へためる。
  3. 最後の MGA-ACK の数と、受け取った数が合ったときだけ保存する。
- **戻す**
  1. `CFG-NAVSPG-ACKAIDING`=1 にする。
  2. 1 通送るごとに MGA-ACK を待つ（IM の flow control）。
  3. 使われた数と、`infoCode` ごとの使われなかった数を数える。
- **ファイルをこの受信機に結びつける。** ファイルには次の 3 つを書いておく。1 つでも違えば戻さない（SD を差し替えたときなど）。
  - SEC-UNIQID
  - MON-VER のファームウェア版
  - 本体の固有 ID（rtc_backup と同じ）
- 書くときは、一時ファイルに書いてから名前を変える。書いている途中で電源が切れても、前の版が残る。
- 書き込みは Core1（タスクキュー）。Core0 は UART で受けて RAM にためるだけ。大きさはまだわからないので、段階 0 で測る。

### 3.2 いつ吸い出すか
- GNSS の UART は 38400bps（約 3.8KB/s）。DBD が 10KB なら UART を約 3 秒使う。その間は NAV-PVT が遅れたり落ちたりしうる。
  **機体（TX 役）では飛行中に吸い出さない。**
- 条件は次のとおり。
  - fix していて、NAV-AOPSTATUS が「計算していない」。
  - 止まっている（自機の対地速度が `READY_STILL_MPS`＝1m/s 以下で 30 秒続いた）。
    計画では「RX 役（ボート）はいつでもよい」としていたが、実装では役によらず止まっているときだけにした
    （ボートも NO SIGNAL のときは自機の GNSS で航法するのと、条件が 1 つのほうが間違えにくいため。ボートも出艇前・帰着後に止まる）。
- 1 回目は最初の fix から 15 分後（ANA の計算が進んでから）、あとは 30 分ごと。

### 3.3 いつ戻すか
- **起動時に時計が死んでいたときだけ**（`gnss_rtc_alive_on_boot()` が false）。生きていれば BBR のほうが新しいので触らない。
- 順番は次のとおり。
  1. PC の時刻（§3.6）か仲間の時刻（§4）が先に入っていれば、MGA-INI-TIME_UTC → MGA-INI-POS_LLH → DBD の順に入れる
     （いまは時刻だけ。位置はまだ）。
  2. まだなら、DBD をすぐ入れて、ACK を数える。
  3. `infoCode`=1（時刻を知らない）で断られたぶんは RAM に残しておき、時刻がわかったら 1 回だけ入れ直す。
     時刻がわかるのは、仲間から時刻が来たとき、または GNSS が自分で衛星から時刻を読んだとき。
  4. RAM は、最初の fix か 30 分で手放す。
- 時刻がわかれば、ファイルの古さもわかる。古すぎるファイル（例: 7 日より前）は使わない。

### 3.4 これだけで縮むか（単独でも効く見込み。ただし DBD が新しいときだけ）
2026-11-09 にユーザーから「BT1 が切れて時刻がわからなくなっても、時刻は比較的短時間で取れる」との指摘があり、見直した。

**時刻は、エフェメリスよりずっと早く手に入る**
- GPS なら、TOW（週の中の時刻）は 6 秒ごとのサブフレームすべてに入っている。週番号は 30 秒ごと（サブフレーム 1）に入っている。
  30 ビットの語が 1 つ正しく読めれば足りる。
- エフェメリスは、1 衛星につきサブフレーム 1〜3（18 秒分）を誤りなく読む必要がある。それを 4 衛星以上で繰り返す。
- なので弱い電波でも、時刻のほうがずっと早く手に入る（ユーザーの実機での感触とも合う）。

**時刻がわかったあとに効く**
- 時刻がわかれば、DBD の予測軌道を残りの衛星に使える。衛星ごとにエフェメリスを読まずに済む。
- アルマナックも入っていれば、どの衛星を探せばよいかがわかる。
- 最初の 1 衛星を見つけるまでの全探索は残る（コールドと同じ）。

**時刻がわかったら DBD を入れ直す手順（§3.3 の 3）が欠かせない**
- 起動直後に入れた分が `infoCode`=1 で捨てられていたら、入れ直さない限り何も効かない。
- 時刻がわかったかは、GNSS が出す時刻の有効フラグで見る。どのメッセージのどのフラグを見るかは、段階 0 で確かめる。
- この動きは資料に書いていない。段階 0 の「DBD だけ」で確かめる。

**効くのは DBD が新しいときだけ**
| 前回使ってからの時間 | BT1 | DBD の中で使えるもの | 効き |
|---|---|---|---|
| BT1 がもつ間 | 生きている | （要らない。BBR にある） | — |
| BT1 が切れてから約 3 日まで | 切れている | 予測軌道 | 大きい見込み |
| 約 3 日〜数週間 | 切れている | アルマナック（入っていれば） | 小さい。見える衛星はわかるが、エフェメリスは読み直す |

- BT1 がもつ時間は、前回の通電時間で決まる（rtc_backup の見積もり）。
  - 1 時間の通電で約 9 時間
  - 3 時間で約 1 日
  - 6 時間で約 2 日
  - 満充電で約 8 日
- なので「短い通電のあと、1〜3 日空けて使う」ときに効く。
- そういう起動がどれだけあるかは、log.txt でわかる。
  - `RTC BACKUP CHECK:` の行が `rtc lost` で、`off` が 72h より短い起動が、DBD が効いたはずの起動。
  - `RTC BACKUP CHECK:` の行は、11-08 に足した未コミットのファームから出る。
  - `GNSS FIXED ... after boot` の秒数と並べれば、段階 0.a になる。

**最初に作るのはこれ。** 無線を使わないので、本来の役割への影響は無い。
影響が出うるのは、吸い出しで GNSS の UART が埋まることだけ。これは §3.2 で、飛行中にはやらないことにしている。

### 3.5 実装（2026-11-09。v7・v7.1 で同じ `gnss_dbd.cpp`）
- **設定**: `settings.h` の `GNSS_DBD_*`（`GNSS_DBD_ENABLE` を 0 にすると全部止まり、RAM も取らない）。
- **GNSS の設定**: `gnss_setup_impl()` の ⑩（v7 は ⑨）で `CFG-NAVSPG-ACKAIDING`=1（RAM）。設定の最後に SEC-UNIQID と MON-VER をポールする。
- **ファイル**: SD のルートの `gnss_dbd.bin`。64 バイトの頭（`GnssDbdHead`。吸い出した UTC・数・大きさ・GNSS の固有 ID・本体の固有 ID・CRC）と、
  MGA-DBD のフレームを受けた順にそのまま並べたもの。一時ファイル `gnss_dbd.tmp` に書き切ってから名前を替える。
  起動時に一時ファイルのほうしか読めなければ、それを本体の名前に替えておく（次の書き込みで一時ファイルを空にしても 1 つ残るように）。
- **RAM**: 24KB（`GNSS_DBD_BUF_BYTES`）。DBD の実際の大きさは資料に無いので、足りなければ log.txt に `too big ... bytes` と全体の大きさが出る。
- **送り方**: UART の送信 FIFO が空いた分だけ書く（Core0 を待たせない）。ほかのコマンドを GNSS へ書く前に `gnss_dbd_finish_tx()` で書き切る（CLAUDE.md）。
  返事が 3 回続けて来なければ、待つのをやめて 50ms 間隔で送る。書き切りが 200ms 終わらなければ残りを捨てる（`GNSS DBD: UART stuck`。Core0 を止めない）。
- **NAV-ORB**: 受信バッファを 768 → 1600 バイトに広げ、戻した直後と入れ直した直後にポールして 1 行にまとめる。
- **打ち切り**（GNSS の掴み直し・リプレイ）でも、送りかけのフレームは `gnss_dbd_finish_tx()` で書き切ってから止める（2026-11-10〜。
  途中で切ると、次に送るコマンド＝掴み直しなら最初の設定コマンドが GNSS に黙って捨てられた）。入れ直し待ち・試験の読み込み待ちは打ち切らない。
  試験の `COLD` でタスクのキューが満杯だったときも、`GNSS DBD TEST: not restored (task queue full)` を残す。
- **リプレイ**: 再生中は吸い出し・戻しを打ち切る。抜けた直後は本物の NAV-PVT が届くまで fix を見ない（偽の fix で戻しの窓や試験の TTFF を
  終わらせないため）。gnss.cpp も抜けるときに日時・位置・fix を無効にする（2026-11-10 までは日時だけで、位置と fix は CSV の最後の行のまま
  残った）。この間、試験コマンドは `ERROR,REPLAY`。
- **試験をしたら自動の吸い出しを止める**: `COLD` / `COLDONLY` / `HOT` を打つと再起動まで（`STATUS` の `auto=off`）。`COLDONLY` で GNSS を
  空にしたあと、fix して 30 秒止まると薄いデータベースで SD のファイルを上書きし、次の `COLD` の比べ物にならなくなるため。`SAVE` は効く。
- **入れ直しを待っている間（`ST_WAIT`）も試験は打てる**（2026-11-10〜）: 試験で上書きする（GNSS をリセットして数え直すので、待っていた
  入れ直しは意味を失う。`COLD` は SD から読み直す）。入れ直しが済んだ・要らないと決まったら待ちを抜ける。
  それまでは fix するか窓（30 分）が終わるまで `ERROR,BUSY` で、屋内で `COLD` を打って時刻が読めないと 30 分次の試験ができなかった。
  `SAVE` は待っている間 `BUSY` のまま（RAM の中身を入れ直しに使うため）。
- **PC 上の試験**: GNSS と Core1 を真似たハーネスで、保存・戻し・入れ直し・別の GNSS・ファイル無し・返事なし・打ち切り（設定し直し／リプレイ）・
  試験コマンド・数の食い違い・大きすぎ・走行中は吸い出さない・リプレイを抜けた直後の偽の fix・試験のあとの自動保存・リセットが効かない・
  UART の詰まり、を確かめた（ハーネスはリポジトリには入れていない）。

**実機で確かめること**（log.txt）
1. `GNSS VER:` が `ROM SPG 5.10` か。`GNSS ID:` が出るか。`GNSS CFG OK .../AckAid` か（`NO ACK: ... ACKAIDING` なら返事が来ない）。
2. `GNSS DBD SAVE (...)`: 数と大きさ・吸い出しの時間。`too big` なら `GNSS_DBD_BUF_BYTES` を上げる。
3. `PONS:DBD,COLD` と `PONS:DBD,COLDONLY` を同じ場所で交互に。`GNSS DBD TEST ...: fix XXs after reset (... time YYs dbd=A/B resend=C/D)`。
   - `notime`（時刻が無くて断られた数）がどれだけあるか、`resend` で使われるようになるか。
   - `time`（GNSS が時刻を知るまで）が fix よりどれだけ早いか（§3.4 の前提）。
   - `GNSS ORB (after restore|after resend)` の ana の数。
4. 実際に BT1 が切れた起動の `GNSS FIXED ... after boot rtc=lost dbd=...` の秒数を、`RTC BACKUP CHECK:` の `off` と並べる。
5. 通信がうまくいっているか: `GNSS DBD IO (...)` の行（2026-11-09 に足した。吸い出し・戻しの 1 回ごと）。
   - `NAV-PVT gap max`: 吸い出しで位置の更新がどれだけ待たされたか（ふだん 500ms）。大きければ吸い出しの条件（止まっているとき）が要る証拠、
     数秒を超えるなら地上でも気になる。
   - `rx peak`（受信 FIFO 4096B のたまりの最大）・`ckerr`・`ovf`: 0 でない `ckerr` / `ovf` はバイトが欠けている。吸い出しの数が合わない原因の手がかり。
   - `ack avg / max / late`: 1 通ごとの返事の遅れ。`late` があれば `GNSS_DBD_ACK_TIMEOUT_MS` を延ばす。`odd` は DBD 以外への返事（来ないはず）。
   - `txwait max`: 画面の切り替えなどが送りかけのフレームを待った時間。
   - ほかに `GNSS DBD SAVE: due ... waiting (理由)`（30 分ごと）、`GNSS ID: no answer ...` / `GNSS VER: no answer ...`、
     `other N (code 5xN)`（断られた理由の内訳）、`GNSS DBD file: ... (read Nms)` / `SAVE ...: sd Nms`（SD の時間）。

**2026-11-11 の結果**（v7.1 実機、1.04 のファームで 13 回起動・車で約 55 分走行）
- 1: 11 回とも `ROM SPG 5.10`・`GNSS ID:`・`CFG OK .../AckAid`。済み。
  （残る 2 回のうち 1 回は GNSS が黙った起動で `NO ACK ... ACKAIDING` と `GNSS VER: no answer`。照度センサーも同時に見つからなかった。TODO §3）
- 2・5: 自動の吸い出しが 2 回。74 通 4800B（吸い出し 1.4 秒）と 118 通 7588B（2.1 秒）。24KB の箱に十分。
  `NAV-PVT gap max` 613 / 674ms、`ckerr 0`・`ovf 0`・`txwait max 0ms`。済み。
- 4: まだ。時計が切れた起動でファイルがあった回が無い（ファイルができる前の `rtc=lost dbd=none(no file)` は 164 秒。§7 の 0.a）。

### 3.6 外から時刻を入れる（2026-11-10。PC の `PONS:TIME`。LoRa も同じ口に渡す）
- **なぜ**: §3.4 のとおり、時刻を知らない GNSS は戻した DBD のうち時刻の要るもの（実機で `notime`）を断り、
  GNSS が衛星から時刻を読むまで入れ直しを待つ。電波が弱いとその待ちが長い。時刻が先にあれば最初から全部受け取られ、
  予測軌道（ANA）もすぐ使える（Integration Manual §3.11.4 も、BBR が無いときは MGA-INI-TIME_UTC を入れるよう勧めている）。
- **入口は 1 つ**: `gnss_dbd_give_time(utc_ms, at_ms, src)`（`gnss_dbd.h`）。`utc_ms` は UNIX 時刻 [ms]、`at_ms` はその時刻だった
  `millis()`、`src` は `GNSS_TIME_SRC_PC` / `GNSS_TIME_SRC_LORA` / `GNSS_TIME_SRC_SELF`（試験）。
  **いつ入れるか・入れ直すか・ログは中（`time_block()` の 1 か所）で決める。** 出どころを足すときは渡すだけにする。
  - いまの呼び出し元は USB シリアルの `PONS:TIME,<UNIX 時刻 ms>`（`.ino` → `gnss_dbd_time_command()`）だけ。
    Flight Viewer が `PONS:READY` を受けるたびに `Date.now()` を送る（docs/pons_webserial_protocol.md）。
  - **LoRa を足すとき**は、受けた側の確かめ（§4.6 の 1.）を済ませてから `GNSS_TIME_SRC_LORA` で渡す。`at_ms` は受けた
    `millis()` から電波に乗っていた時間（`e220_airtime_ms()`）と、送る側がフレームを作ってから送るまでの遅れを引いた値にする。
    2 秒ごとに呼んでよい（入れないときはすぐ戻り、ログも覚え始めの 1 回だけ）。精度は `GNSS_TIME_ACC_LORA_MS`（2 秒）。
- **入れる条件**（`time_block()`）:
  - 起動後最初の NAV-PVT を見て、GNSS が時刻を知らない（NAV-PVT に日時が無い）とき。知っていれば入れない（`NOT_NEEDED`）。
    GNSS の時刻のほうが正確なので、BT1 が生きている起動では何もしない。
  - 起動直後で時計の生死がまだ分からない・GNSS がつながっていないときは覚えておき（`LATER`）、入れられるようになったら入れる。
    覚えた時刻は、入れるときにその時点まで進め、本体の時計のずれ（100ppm）を精度に足す。
  - 受け取られたら（MGA-ACK type=1）、この GNSS には入れない（`ALREADY`）。断られた・返事が無いときは 60 秒あけて 3 回まで
    （`GAVE_UP`）。GNSS を掴み直したら（GNSS だけのリセット）数え直す。
  - 机の上の試験（`COLD` / `COLDONLY` / `HOT`）の間は入れない（`TEST`）。リプレイ中・抜けた直後も入れない（`REPLAY`）。
- **入れ方**: UBX-MGA-INI-TIME_UTC（24B）。`ref.source`=0（受け取った瞬間）、`leapSecs`=−128（知らない）、`trustedSource`=0、
  精度は `GNSS_TIME_ACC_PC_MS`（2 秒）。書き終わるまでの約 8ms を足す。DBD のフレームを書きかけていたら先に書き切る。
- **入れ直し**: 時刻が受け取られたら、それを「GNSS が時刻を知った」として、断られていた DBD をすぐ入れ直す（NAV-PVT に日時が
  出るのを待たない）。ログは `GNSS DBD: GNSS time given (pc) 1.7s after boot`、fix の行は `time=1.7s(pc)`。
- **PC の時計があてになるか**: 伝えた精度より外れていると、GNSS の性能はかえってかなり落ちる（Interface Description §3.13.9.3）。
  最初の fix で、入れた時刻が本当はどれだけずれていたかを `GNSS TIME (pc): given time was +0.08s off at 1st fix (told acc 2.0s)` に残す
  （NAV-PVT が測位の瞬間より遅れて届くぶん、少し + に出る）。精度より大きければ ` ** more than acc **`。
- **机の上の試験**: `PONS:DBD,COLD,TIME`（§7 の「DBD ＋ INI」）と `PONS:DBD,COLDONLY,TIME`（「INI だけ」）。リセット前に本体が覚えた時刻
  （最後の NAV-PVT の時刻と、それを受けた `millis()`）を、PC・LoRa から来た時刻の代わりに同じ口・同じ精度で入れる。
  `COLD,TIME` は、GNSS が立ち上がり直したら時刻を入れてから DBD を戻す（5 秒入れられなければ時刻なしで戻す）。
- **PC 上の試験**（ハーネス）: 最初の NAV-PVT より前に来た（覚えて、戻す前に入れる → 断られない）・戻している途中に来た（残りは使われ、
  断られた分はすぐ入れ直す）・受け取られたが NAV-PVT にまだ出ない・時計が生きている（入れない）・ありえない時刻・形の違い・
  断られ続ける（60 秒ごとに 3 回）・返事が無い・リプレイ・`COLD,TIME` / `COLDONLY,TIME` / 素の `COLD` の最中の `PONS:TIME`、を確かめた。
  前からある試験の結果は変わらない。

**実機で確かめること**（log.txt）
1. `GNSS TIME (pc): gave ... -> accepted`（`refused code N` なら GNSS が受け付けていない。`no answer` なら返事の設定）。
2. `PONS:DBD,COLD,TIME` と `PONS:DBD,COLD` を同じ場所で交互に。`TEST cold+dbd+time: fix XXs ... dbd=A/B` の `notime` が 0 になるか、
   fix がどれだけ早いか。`COLDONLY,TIME` と `COLDONLY` も（時刻だけでどれだけ効くか）。
3. PC につないで BT1 が切れた起動（屋内でよい）: `GNSS TIME (pc)` → `GNSS DBD: GNSS time given (pc)` → `RESTORE resend` が続くか。
   そのまま外へ持ち出して `GNSS FIXED ... time=...(pc)` の秒数。
4. `given time was ... off`: PC の時計のずれ。2 秒に近い・超えるなら `GNSS_TIME_ACC_PC_MS` を見直す。

**2026-11-11 の結果**: 1 は済み（屋内で `accepted (ack 29ms, try 1)`。時計が分かっているときは `NOT_NEEDED`）。
屋内のまま測位しなかったので 2〜4 はまだ。

## 4. 手 2: 仲間から時刻をもらう（段階 2。ビーコン。2026-11-13 実装・実機未確認）

> **2026-11-13 決定: 無線で GNSS へ入れるのは時刻だけ。** 位置（MGA-INI-POS_LLH）は入れない。ビーコンの並びには位置も載せてある
> （32 バイト固定で電波の時間は増えず、並びは後から変えにくいので先に入れた。使うかは §8 の机の上の試験で決める）。
> 印は `0x58`。**別のグループの時刻は使わない。** 要求ビーコンも作った（ボート同士）。
> 実装は `link_assist.cpp`（v7・v7.1 で同じ中身）、並びは `lora_link/link_beacon.h`、定数は `settings.h` の `LINK_ASSIST_*`。
> PC の試験台（GNSS・E220・時刻を真似たもの。リポジトリには入れていない）で、§4.1〜4.6 の動きを確かめた（§4.7）。

### 4.1 誰が誰を助けるか
| 困っている側 | 時刻の出どころ | 新しく送るもの |
|---|---|---|
| ボート（GNSS が時刻を知らない） | **機体のテレメトリ**（回転枠 0 の日付と時 ＋ 毎回の 0.1 秒時刻） | **なし** |
| 機体（同じ） | 時刻を持つボート・予備機の**提供ビーコン** | ボートの提供 |
| ボート（機体が fix していない・いない） | ほかのボートの提供ビーコン | 困っている側の**要求ビーコン**と、提供 |

- 提供ビーコンは同報なので、1 発で機体も困っているボートもまとめて助かる。
- 効くのはほぼ**時刻**。DBD のうち時刻が無くて断られる分（`notime`）が最初から受け取られ、ANA がすぐ効く。
  縮むのは「GNSS が衛星から自分で時刻を読むまで」（fix の行の `time=XXs`）。**DBD が無い・古いときは、時刻をもらってもほとんど効かない**
  （軌道を知らないので探す先が決まらない）。値打ちは悪い場所で `PONS:DBD,COLD` と `PONS:DBD,COLD,TIME` を交互にすれば測れる（§3.6）。
- **テレメトリの回転枠 0 は UTC**（送信機は GNSS の UTC の日付と時をそのまま載せる。2026-11-13 にコードで確かめた。pons_link.md の
  「JST」は誤りだったので直した）。受け始めは時が 0 のままなので、**枠 0 を受けて時と日付が分かってから**使う（`link_w2_utc_ms()`）。
  時刻が「無し」（0xFFFF）のフレームも使わない。
- **送信機の fix は条件にしない**（2026-11-13 夕方に変更。ユーザー「RTC の時刻も共有すべき」）。BT1 が生きている機体は、起動 2 秒ほどで
  GNSS の時計（RTC）の時刻を出す（11/11〜13 の log.txt の `GNSS TIME: ... UTC` はどれも fix の前）。ただし RTC の時刻は切っていた時間だけ
  ずれうる（32kHz の水晶 ±20ppm で 1 日 1.7 秒、1 週間 12 秒。受信中に GNSS が合わせ込むので実際は小さいはず）ので、**精度をつけて渡す**。
  - 送信機は自分の GNSS の NAV-PVT tAcc から status に立てる: 1 秒以内は 0（古い送信機と同じ）、1〜4 秒は `LINK_ST_TIME_COARSE`（0x0800）、
    4 秒より悪い・分からないは `LINK_ST_TIME_BAD`（0x1000）。**tAcc は 32 ビットの ns なので 4.29 秒で頭打ち**で、それ以上は分からない。
  - ボートは BAD なら使わない。COARSE なら精度 5 秒（`LINK_ASSIST_TACC_MAX_MS` ＋ `LINK_ASSIST_TACC_MARGIN_MS`）、それ以外は 2 秒と伝える。
  - 止まった時刻（送信機の GNSS が黙った）は、同じ送り主の 2 発の確かめで弾く（§4.6）。
  - 自分の時刻の精度は log.txt の `LINK ASSIST: own time tAcc 0.850s (no fix yet, rtc=alive)` と `(at first fix ...)` に出る。RTC の時刻が
    実際どれだけ確かかは、これを集めれば分かる。
  - **確かめられていない時刻は渡さない**（2026-11-14〜。`gnss_own_time_trusted()`）。渡すのは BT1 が保っていた RTC の時刻と、この起動で fix したあとの時刻だけ。
    外から入れた時刻（LoRa・PC）と、fix の前に GNSS が自分で読んだ時刻は、fix するまで渡さない（機体は status に `LINK_ST_TIME_BAD`、ボートは提供しない）。
    fix していないときに時刻が飛んだ・消えたときも、次の fix まで渡さない。
    **きっかけ**: 11/14、v7 の受信機（主基板 F）が機体のテレメトリから正しい時刻をもらったあと、fix しないまま 4〜15 分たって GNSS の時刻が
    約 +17 分（985〜1023 秒）飛んだ（2 回。追っている衛星 5〜10 機・C/N0 15〜22・使っている衛星 0）。画面の時刻と log.txt が飛び、
    その時刻を仲間へ渡していれば機体のコールドスタートを壊すところだった。GNSS の中で何が起きたかは未確定なので、
    飛びを `GNSS TIME JUMP:` の行に残す（`GNSS_TIME_JUMP_MS` 2 秒以上。前後の valid・flags2・tAcc・fix・衛星数）。
- テレメトリの時刻は「最後の NAV-PVT（2Hz）の時刻」なので、受けた時点で 0.06〜0.56 秒古い。平均の `LINK_ASSIST_TELEM_AGE_MS`（300ms）を足して
  ずれを ±0.25 秒にそろえる（試験台の値）。

### 4.2 ビーコンの形（32 バイト。テレメトリと同じ長さ。`lora_link/link_beacon.h`）
| バイト | 中身 |
|---|---|
| 0 | 印 6 ビット（`0x58`）＋ グループ 2 ビット（テレメトリと同じ） |
| 1 | seq（送るたびに 1 つ進める。ログ用） |
| 2 | 種類 2 ビット（1 = 要求、2 = 提供）＋ 版 2 ビット（いまは 0。知らない版は読まない）＋ 位置あり 1 ビット |
| 3 - 6 | UTC の秒（2020-01-01 から）。要求は 0xFFFFFFFF |
| 7 - 8 | その秒の中の ms（0〜999）。要求は 0xFFFF |
| 9 - 10 | 送り主の短い ID（本体の固有 ID の CRC16） |
| 11 | 送り主の衛星数（ログ用） |
| 12 - 19 | 緯度・経度（1e-7 度。位置ありのときだけ） |
| 20 - 21 | GNSS 高度 [m] |
| 22 - 23 | 送り主の時刻の精度 [ms]（NAV-PVT tAcc。fix の前の RTC の時刻でも入る。0xFFFF = 分からない） |
| 24 - 29 | 0（予備） |
| 30 - 31 | CRC16-CCITT（テレメトリと同じ） |

- 長さをテレメトリと同じにしたのは、e220.cpp の受信が 32 バイト＋RSSI で切り出しているから。切り出しは印と CRC で両方を拾い
  （`link_frame_is_magic` / `link_frame_valid`）、link.cpp の `link_recv_telem()` がビーコンを `link_assist.cpp` へ渡す。
  **受信の数・RSSI・seq・ミラー・NO SIGNAL・DUP SENDER・GROUP X FOUND・送信前チェック・チャンネル調査には混ぜない。**
- 印 `0x58` はテレメトリの `0xA4`（と古い `0xA2`、65 バイト時代の `'P'`）と 6 ビットとも違う。テレメトリの印は版を変えるたびに 4 つ飛ばしで
  上がる（`0xA8` …）ので、当分ぶつからない（`static_assert` で止める）。
- 提供の時刻は「UART へ書き始めた瞬間の UTC」。送り主は最後の NAV-PVT の時刻に、それを受けてからの `millis()` を足して作る
  （NAV-PVT が 3 秒より古い・fix していないときは送らない）。

### 4.3 機体（送信機）
- **窓を開ける**: 起動後最初の NAV-PVT で GNSS が時刻を知らないと分かったとき（`gnss_dbd_time_want()` が YES。判断は `time_block()` と同じところから出す）。
- **窓の間**: テレメトリの status に **`LINK_ST_TIME_WANTED`（0x0400）** を立てる。送信のあとも E220 を mode 3 に落とさず mode 0 で聞き、
  提供ビーコンだけを拾う。1Hz の送信はタイミングも中身も変えない。
- **窓を閉じる**: GNSS が時刻を受け取った（MGA-ACK）・衛星から自分で読んだ・机の上の試験・`LINK_ASSIST_WINDOW_MAX_MS`（30 分）。
  閉じたら送信の合間に寝かせ直し、ビットを下ろす。**その起動の間は二度と開けない。**
- 無線 OFF・`link_assist:OFF`・リプレイ中・デモ中は、窓を**閉じずに止めておく**（無線モードは回転式で OFF を通ることがあり、閉じると戻らないため）。
- WIRELESS 画面の受信機の `Sender :` 行に ` TIME?`（橙）と出る。故障ではないので赤にしない（`LINK_ST_NOT_FAULT`）。

### 4.4 ボートの動き
**困っているボート**（GNSS が時刻を知らない。窓はボートにも同じく開く）
1. 機体のテレメトリ（§4.1 の条件）と提供ビーコンの時刻を使う。
2. 窓を開けてから `LINK_ASSIST_REQ_WAIT_MS`（10 秒）たっても、時刻の出どころ（使える時刻の載った機体のテレメトリ・提供）も機体の頼み（`LINK_ST_TIME_WANTED`）も
   直前 10 秒に聞こえていなければ、要求ビーコンを `LINK_ASSIST_REQ_INTERVAL_MS`（10 秒）に 1 回送る。
3. 直前 10 秒に同じグループの別のボートの要求が聞こえていたら送らない（提供は同報なので、要求は 1 台ぶんで足りる）。
4. 窓が閉じたら止める。

**助けるボート**（自分の GNSS が精度 4 秒以内の時刻を持っている。fix は要らない。予備機も同じ。受信役のときだけ）
1. 直前 `LINK_ASSIST_ASK_HOLD_MS`（15 秒）に「頼み」を聞いていれば提供する。頼みとは、機体の最新のテレメトリの `LINK_ST_TIME_WANTED` か、
   同じグループの要求ビーコン。機体のビットが下りたら次のフレーム（約 1 秒）でやめる。
2. 間隔は `LINK_ASSIST_OFFER_MIN_MS`（2 秒）。ローワーでは機体の 2 周期に 1 回。アッパーでは自分の休止（送信時間の 10 倍）が明けてから。
3. 2 台以上いるときは §4.5 で 1 台にしぼる。

### 4.5 かぶらないようにする
**枠**（`lassist_slots()`。機体のテレメトリを受けた時刻 t0 から）
- 最初の枠は t0 ＋ `LINK_ASSIST_SLOT_FIRST_MS`（300ms）。受信機は受けた直後に地図を描く（`LINK_DRAW_BUDGET_MS` 250ms）ので、その後ろにする。
- アッパーバンドは、機体の休止（送信時間の 10 倍）が明けてから。**休止の間に E220 が受けられるかは資料に無い**（~/Downloads にあるのはメーカーの
  送信時間の表だけ）ので、受けられなくても届く位置にした。
- 枠の幅は自分が塞がる時間（送信時間の約 1.5 倍）＋ `LINK_ASSIST_SLOT_SEP_MS`（60ms）。最後の枠は、終わってから機体の次の送信まで
  `LINK_ASSIST_SLOT_GUARD_MS`（50ms）残るところまで。最大 3 つ。

| 帯域 | SF | 機体の周期 | 枠（t0 から ms） |
|---|---|---|---|
| ローワー | 7 | 1.0 秒 | 300 / 423 / 546 |
| ローワー | 8（既定） | 1.0 秒 | 300 / 465 / 630 |
| ローワー | 9 | 1.0 秒 | 300 / 540 |
| ローワー | 10 | 1.0 秒 | 300 のみ |
| ローワー | 11 | 1.0 秒 | **入らない → 提供も要求も送らない**（log.txt に `no slot` を 1 回） |
| アッパー | 7 | 1.0 秒 | 470 / 593 / 716 |
| アッパー | 8 | 1.16 秒 | 750 のみ |
| アッパー | 9 | 1.98 秒 | 1250 / 1490 |
| アッパー | 10 | 3.45 秒 | 2140 / 2513 |

**譲り合い**
1. 枠が 2 つ以上なら、毎回くじで 1 つ選ぶ。1 つしかなければ、その回に送るかを 1/2 のくじで決める。
2. 同じ回に、自分の枠より前に別のボートの提供が聞こえたら、その回は送らない。
3. **休む決まり**: 直前の「提供の間隔 × `LINK_ASSIST_YIELD_OFFERS`（3）」（ローワーで 6 秒）に別のボートの提供が聞こえていたら、自分は送らない。
   落ち着いたあとは 1 台だけが送り、そのボートが止まったり離れたりして 3 回ぶん聞こえなくなったら、休んでいたほうが引き継ぐ。
4. 同じ枠を引いてかぶったら、次の回にくじを引き直す（2 台なら 1 回でかぶる確率は 1/3）。
5. 描画などでループが遅れ、枠の時刻を `LINK_ASSIST_SLOT_LATE_MS`（40ms）過ぎていたら、その回は送らない（ずれた時刻に送らない）。
6. 機体が聞こえないとき（ボート同士）は、いまから 0.3〜1.0 秒後のどこか。
7. 要求も同じ枠とくじを使う。

**E220 のキャリアセンスでは防げない**（2 台が同時に「空いている」と見て送り始める。PONS 同士は少し離れると相手の送信が見えない）。

**電波法**: ローワーは休止 50ms なので、2 秒に 1 回で問題ない（SF8 で占有率 3.5%）。アッパーは「送信時間の 10 倍休止」を枠と間隔で守り、
提供は頼まれている間（多くは数秒〜数十秒）だけなので「1 時間 360 秒以下」も収まる。

### 4.6 受けた時刻の確かめ（機体・ボート共通。`consider_time()`）
1. ビーコンは、CRC・印・**同じグループ**・種類が提供・送り主が自分でない、のものだけ。版が違えば読まない。
2. **2 発で確かめる**: `LINK_ASSIST_PAIR_MIN_MS`（1.5 秒）以上離れた 2 発で、UTC の差と受けた `millis()` の差が `LINK_ASSIST_PAIR_TOL_MS`
   （0.7 秒）以内で合うこと。止まった時刻（2 秒離れた 2 発で 2 秒食い違う）・時の繰り上げの取り違え（1 時間）を弾く。**同じ送り主の 2 発で組にする**（2026-11-13 夕方〜。精度の違う送り主＝RTC の時刻の機体と
   fix しているボートの時刻を組にすると、どちらも正しいのに食い違って見え、いつまでも入れられないため。送り主ごとに 1 発目を持つ）。
   食い違ったらそれを 1 発目にして数え直す（log.txt に 1 起動 5 行まで）。60 秒より古い 1 発目は捨てる。
3. 通ったら `gnss_dbd_give_time(utc_ms, at_ms, GNSS_TIME_SRC_LORA)`。`at_ms` は受けた `millis()` から送信時間と UART の 33 バイト（約 3ms）を
   引いた値。GNSS へ伝える精度は、送り主の精度が 1 秒以内なら `GNSS_TIME_ACC_LORA_MS`（2 秒）、1〜4 秒ならテレメトリは 5 秒・ビーコンは
   送り主の精度 ＋ 1 秒（`gnss_dbd_give_time()` の 4 つめの引数）。入れるか・入れ直すかは `time_block()` が決める（ここに条件を足さない）。
4. `gnss_dbd_give_time()` 側でも、ビルドした日より前・2100 年以降・**SD の DBD を吸い出した時刻より前**の時刻は `BAD_TIME` で断る
   （最後のものは 2026-11-13 に足した。PC の時刻にも効く）。
5. RSSI は距離の目安にしない（ログに残すだけ）。

### 4.7 PC の試験台で確かめたこと（2026-11-13）
- ビーコンの並びの往復（位置・負の値・要求・知らない版を読まない・CRC）、テレメトリの印と全グループで見分けがつくこと
- 枠の表（上）。どの枠も機体の次の送信の手前で終わり、互いに重ならず、アッパーでは機体の休止の外にある
- ボートがテレメトリから時刻を得る: 枠 0 の前は使わない、大みそかの 23:59 → 元日 0:00（時と日付と年の繰り上げ）をまたいでも正しい、
  ずれ ±0.25 秒。時刻「無し」・止まった時刻は使わない。機体の時刻が聞こえていれば要求を送らない
- 提供（ローワー SF8・SF10・SF11、アッパー SF8・SF10）: 枠の中だけで送る、間隔 2 秒以上（アッパーは休止も）、送る時刻のずれ 60ms
  （試験台の NAV-PVT の遅れ）、機体のビットが下りたら次の周期でやめる、ローワー SF11 は送らない、別のボートが送っていると休み、止まると引き継ぐ
- 機体: 最初の NAV-PVT の前は窓を開けない、別グループの提供は使わない、1.5 秒未満の 2 発では入れない、1 時間ずれた提供は入れない、
  チャンネル調査中は起こしたままにしない、OFF を通っても・リプレイを挟んでも窓は残る（止めている間は使わない）、閉じたら開け直さない、機体は送らない
- 要求: 10 秒聞いてから 10 秒ごと、別のボートが頼んでいる間は黙る、提供が聞こえたら黙る、窓が閉じたら送らない
- RTC の時刻（2026-11-13 夕方に足した）: fix していない機体の時刻（精度 1 秒以内）を使う、`LINK_ST_TIME_BAD` なら使わない、`COARSE` なら精度 5 秒と
  伝える、精度の違う 2 つの送り主が交互に来ても両方入れられる、精度が分からない・4 秒より悪いビーコンは使わない、fix していないボートが RTC の時刻で
  提供する（ビーコンに精度 600ms）・精度が悪くなったら提供しない、送信機の status のビット（よい 0 / COARSE / BAD / 時刻なし 0）。
  **tAcc を ms に切り上げる計算が大きな値で溢れて「とても確か」に化ける誤りをここで見つけて直した**
- **確かめていないこと**（実機）: E220 の受信役のままの送信（AUX・受信バッファ。`LINK ASSIST: 60s` の `noRf` / `busy`）、機体が送信の合間に
  起きたままで 1Hz の送信が崩れないか（ボートの `LINK RX` の `miss`）、アッパーバンドの休止中の受信、ボートの地図の描画と枠の遅れ（`late`）、
  2 台のボートのかぶり、**送信機の RTC の時刻の精度**（`LINK ASSIST: own time tAcc ... (no fix yet, rtc=alive)` を `RTC BACKUP CHECK:` の `off` と並べる。
  4.29 秒の頭打ちばかりなら RTC の時刻は渡らない）。
  - **`PONS:DBD,COLD` / `COLDONLY` / `HOT` の試験中は外からの時刻（LoRa も）を入れない作り**なので、ボートへ渡るかの確かめは本当に BT1 が切れた起動で。
  - 地図の下の時刻は受信機自身の GNSS が NAV-PVT に時刻を出したときだけ出る。時刻を入れたあと NAV-PVT に出るかは未確認なので、
    入ったかは log.txt の `LINK ASSIST: time from ... -> SENT` と `GNSS TIME (lora): ... accepted` で見る（2026-11-13、v7 の受信機に出なかった件）。

  - 場所は、空が開けたところと、窓ぎわ・車内のような悪いところの 2 つ。アンテナは同じものを使う。
  - 試験用のシリアルコマンドは段階 1 と一緒に作った（USB シリアルの `PONS:DBD,SAVE / COLD / COLDONLY / HOT / STATUS`。
    結果は log.txt の `GNSS DBD TEST ...`）。「INI だけ」「DBD＋INI」は `COLDONLY,TIME` / `COLD,TIME`（2026-11-10〜。いまは時刻だけで、
    位置は入れない）。ANA 無効のコールドは、
    `GNSS_USE_ANA` を 0 にしたファームで `COLDONLY`（`COLDONLY` は ANA をその起動で決めたままにするので。§2.5）。
