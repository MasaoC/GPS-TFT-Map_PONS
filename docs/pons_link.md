# PONS Link — 機体⇄ボート テレメトリ・ダウンリンク

同一ファームウェアの PONS を 3 台つくり、設定で役割を決める。

| 役割 | 台数 | 置き場所 |
|---|---|---|
| 送信機 (TX) | 1 | 機体 |
| 受信機 (RX) | 2 | 追走ボート／プラットフォーム |

目的は、**パイロットに出ている航法画面をボート側でそのまま再現すること**。
通信は**下り一方向のみ**で、受信側から機体へ返すものは何も無い。

---

## 1. 役割とモード

設定ファイルの `link_mode` で決める（`OFF` / `TX` / `RX`）。3 択のトグルなので
**「送受同時 ON」を表現できない**。取り違えは起動時の音声で気づく。

- `TX` — 従来どおり自機を表示しつつ、1Hz でテレメトリを送信する
- `RX` — 受信したテレメトリで画面をミラー表示する。送信はしない
- `OFF` — 無線を使わない

### グループ ID

同じ会場に**別チームの PONS** がいたときに取り違えないための識別子。

CH と SF が偶然一致すると、magic も ver も CRC も通ってしまう。つまり今までは
**「CH/SF の一致」が事実上のペアリング**だった。同じ機体を他チームに頒布している以上、
これだけでは足りない（受信側が他機の飛行をミラーし、`received/` にも他機のログが残る）。

- **既定は 0。ソースにも SD の雛形にも 0 しか書かない。** 実際の値は各機の
  `settings.txt`（`link_group`）にだけ置く。**git に載るのは仕組みだけで値ではない。**
- 他チームが既定 0 のままなら、こちらが 0 以外にするだけで分離できる
- 電波の設定ではなく**ペイロードの中身**なので、変更してもモジュールへの書き込みは要らない
- 範囲は 0〜255。ただし**設定画面の長押しは +1 ずつ**なので、実運用では
  小さい値（1〜20 程度）にすること。SD が飛んで 0 に戻ったとき現地で押し戻せる

**★ グループ違いは「無信号」と区別して表示する。**
`Signal : GROUP 3 FOUND` のように、**電波は届いていてグループだけ食い違っている**ことを出す。
ここを黙って無反応にすると、SD が 0 に戻った事故が距離不足や故障と区別できなくなる。

> セキュリティではなく**衝突回避**。仕組みは公開されているので、
> 値を知られたくないという以上の保護にはならない。

**★ 受信機側の「全 Ch/SF 自動スキャン」は採らなかった。**
「無信号のとき、実は Ch や SF の設定違いだった」を機械的に見つける案を検討したが、
やめた理由は 3 つ。

1. **単に遠いだけの場合に、聴取をやめてしまう。** 13ch × 5SF = 65 通りを 1 通り 2 秒
   でも 130 秒かかる。その間ずっと本来の設定を聴いていない。復帰を一番知りたい
   タイミングで、一番聴いていないことになる
2. **第三者の信号を掴む。** 920MHz 帯は Wi-SUN スマートメーター等と共用なので、
   「何か受かった」だけでは判断材料にならない。掴んだものが PONS かどうかは
   結局 magic + ver + group で見るしかない
3. **設定違いは飛ぶ前に潰すべきもの**で、飛行中に自動で直す種類の問題ではない

代わりに、**設定を変えた時点で人に確認させる**（次項）ことと、
**グループ違いを無信号と区別して表示する**ことの 2 つで対処する。
どちらも聴取を止めないし、飛行中に勝手に設定が変わることもない。

### 設定を変えたら伝える

`Ch` / `SF` / `Group` は **3 台すべてで一致していないと通信できない**。
1 台だけ変えて伝え忘れると、症状は「無信号」になり、現場では距離や故障と区別が付かない。

- 設定画面に常設で `^ 3 units must match` を出す（変更後に警告するより、変更する前に見せる）
- 無線画面を出るときに 3 つのどれかが変わっていたら、**音声で知らせて SD ログに残す**
  （`wav/link_setting_changed.wav`「送信機と受信機の設定が一致していることを確認してください」。
  ファイルが無ければ 500Hz×2 が鳴るので無音にはならない）
- **送信機・受信機のどちらでも鳴らす。** 受信機側を触って戻し忘れる事故も同じだけ起こるし、
  受信機は 2 台あるぶん取り違えやすい

### 3 台の役割

| 置き場所 | モード | 役割 |
|---|---|---|
| 機体 | TX | パイロットの航法装置。これが本番 |
| 追走ボート | RX | 機体の画面を再現する。ボートマンが見る |
| プラットフォーム | RX → 途中で OFF | **予備機**。機体の PONS が壊れた／電池切れのとき TX へ切り替えて載せ替える |

プラットフォーム機は機体が離れると当然ロストする。**これは想定どおり**で、
ロストを画面と音声の両方で知らせたあと、**人が OFF にする**運用にする。
「ロストしたら自動で静かにする」ようにはしない ― 予備機である以上、
電波が来ているかどうかは常にはっきり分かるほうがよい。

**起動時に TX / RX のどちらも音声で読み上げる。** 片方だけ読み上げる案だと
「何も言わない＝正常」と受け取られ、無線が OFF になっていることに気づけない。
両方読み上げれば**無音が「OFF」を意味する**ようになり、3 状態が音だけで判別できる。

### 送信機の重複検出

送信機が 2 台同時にいるのは異常事態（機体用とボート用の取り違え等）。
**`seq` の逆行**で検出する。送信機が 1 台なら `seq` は必ず増えるので、
減る・止まるのは 2 台いる証拠になる。10 秒以内に 3 回たまったら警告する
（送信機の再起動でも 1 回だけ起きるため、間隔が空いたら数え直す）。

> 送信元 ID を載せて比較する案は却下した。既定値が 3 台とも同じになるため、
> 「設定を触っていない 2 台がどちらも TX」という**一番ありそうな誤設定で
> 黙って失敗する**。運用に依存しない `seq` のほうが確実。

**検出できるのは受信機だけ。** 送信機は送信の合間スリープしていて受信できない。

## 2. 無線とハードウェア

モジュールは **E220-900T22S(JP)**（920MHz LoRa、技適取得済・免許不要）。
RP2350 から UART で直結する。

| 信号 | RP2350 | 備考 |
|---|---|---|
| UART1 TX → E220 RXD | GPIO8 | |
| UART1 RX ← E220 TXD | GPIO9 | |
| E220 AUX → RP | GPIO30 | 状態通知。100nF を GND へ |
| E220 M0 + M1（結線） | GPIO35 *or* GPIO41 | 0Ω で選択。BNO085 のバス構成と排他 |
| E220 VDD | +3V3 直結 | **VCC は開放**（排他利用）。10µF + 100nF |
| E220 ANT | — | IPEX コネクタを使用 |

- **M0 と M1 は結線して GPIO 1 本で駆動する。** 使うのは mode 0（通常送受信）と
  mode 3（Config/DeepSleep）の 2 つだけなので、データシート 5.3 が明示的に許している。
  WOR は使わない。
- **M0/M1 はモジュール内部で 80kΩ プルアップ**されている。外部プルアップ不要で、
  フローティングでも mode 3 に落ちるため電源投入時に勝手に送信することはない。
- **ピーク電流は 43mA ではなく約 150mA。** 43mA は送信時の平均で、モジュール内部の
  ピーク給電はこれに達する。3.3V レギュレータの余裕とバルクコンデンサを確保すること。

### 無線パラメータ

| 項目 | 値 |
|---|---|
| 帯域幅 | 500 kHz |
| 拡散率 | **SF8（既定）**。設定で SF7〜SF11 |
| チャンネル | **CH0〜12（920.8〜923.2MHz）に限る** |
| 送信出力 | 13dBm（20mW） |
| 送信方法 | **トランスペアレント（固定送信にしないこと → §6）** |

`link_radio_prof` は `0=SF7 / 1=SF8 / 2=SF9 / 3=SF10 / 4=SF11`。
SF を 1 段上げると 2.5dB 強くなるが、**送信時間＝送信電流が倍々に増える**。

**CH13 以上を使ってはいけない。** CH0〜12 は 1 回の送信ごとの休止が 50ms 固定で、
400ms 制限も「休止＝送信時間の 10 倍」も 1 時間 360 秒の総量制限もかからない。
CH13〜30 はこれらが全部かかり、サブパケット長も 32B に強制される。

## 3. タイミングと省電力

本体は低輝度で約 72mA、電池は 860mAh。

- **送信は 1Hz。連射しない。** 1 回落ちても実用上困らず、連射は送信電流と
  電波占有時間を素直に倍にするだけ。

### 送信時間と消費電流（ペイロード 65B・BW500kHz）

**SF8 の 98.4ms はメーカー公開の「E220-900T22X(JP) LoRaデータ送信時間計算表」の値**。
他の SF はそこからの概算で、**同じ表から取り直すこと**（下の注意を読むこと）。
消費電流はデータシートの 送信 43mA @13dBm / 受信待機 8.2mA / mode 3 2.5µA から。

| SF | 送信時間 | 1Hz 運用の平均電流 | 電波占有率 |
|---|---|---|---|
| SF7  | 約 55 ms  | 約 2.4 mA  | 5.5% |
| **SF8（既定）** | **98.4 ms（実値）** | **4.3 mA** | 9.8% |
| SF9  | 約 180 ms | 約 7.8 mA  | 18% |
| SF10 | 約 340 ms | 約 14.7 mA | 34% |
| SF11 | 約 600 ms | 約 25.8 mA | 60% |

> ★ SF8 以外は「SF が 1 段上がるごとに送信時間が約 1.8 倍」という LoRa の性質から
> 外挿しただけの概算。一般の LoRa 計算式（CR4/5・プリアンブル 8 を仮定）だと
> SF8 で 53.9ms となり、**メーカー表の 98.4ms と 1.8 倍ずれる**。
> どの仮定が違うのか 1 点からは特定できなかったので、
> **他の SF もメーカー表の値に置き換えること。**

- **送信機の瞬間電流は 43mA**（モジュール内部のピーク給電は約 150mA）。
  平均は SF8 で **4.3mA**。本体 72mA に対して 6% で、電池持ちへの影響は小さい。
- **受信機は瞬間・平均とも 8.2mA**（常時 mode 0）。受信中も待機中も同じ。
  本体 72mA に対して 11%、電池持ちで約 1 時間ぶん短くなる。
  → **受信機のスリープは今後実装予定**（§9）。実装すれば 8.2mA より確実に下がる。
- SF を 1 段上げると **感度は 2.5dB、送信時間と電流は約 1.8 倍**。
  SF8→SF10 は +5dB と引き換えに 4.3mA→約 14.7mA になり、
  **電波占有率も 10%→34% へ上がる**。1Hz を保てる上限は SF11 あたり
  （約 600ms + 休止 50ms で 1 秒スロットの 2/3 を使う）。
- 1 回の送信ごとに 50ms の休止が入る（CH0-12 の規定）。

### 上りの通信を持たない理由

ACK や KEEPALIVE を持つと、受信機 2 台ぶんの衝突回避、送信機側の受信待機、
状態機械の分岐がすべて必要になる。得られるのは「受信機がいない間の送信電力の
節約」だけで、送信は SF8 で平均 4.3mA しかない。**払うコストに見合わない。**

安全上も、上りが無ければ**受信機側の不具合が飛行中の機体へ波及する経路が
原理的に存在しない**。大会レギュレーション上も説明しやすい。

## 4. UART と電波に載せるもの

| | |
|---|---|
| 通常運用 (mode 0) | **115200 8N1** |
| 設定時 (mode 3) | **9600 8N1 固定**（レジスタ設定に関わらず） |

**9600 では `write()` が Core0 を 37.5ms 止める**（68 バイト、ハード FIFO 32B、
arduino-pico に送信バッファは無い）。115200 なら 3.1ms。マップ描画 64ms と
合わせて許容できないため 115200 を使う。

**★ 1 回の `write()` にまとめて渡すこと。分割して書かない。**
E220 は「一定時間データが来ない」ことをパケットの区切りとみなす
（115200bps で >2ms、9600bps で >5ms）。途中で途切れると
**1 回のテレメトリが 2 回の電波発射に分裂**し、占有時間も電力も倍になる。
`write()` はブロックするので、まとめて渡す限り隙間はできない。

### ペイロード

`LinkTelem`（**65 バイト固定**、`lora_link/link_proto.h`）。
`static_assert(sizeof(LinkTelem) == 65)` でビルド時に止めてある。
65 バイトという数値は送信時間・送信電流・電波法の検討がすべて前提にしているので、
項目を足して黙って伸びると検討が全部ずれる。

| 位置 | 内容 |
|---|---|
| ヘッダ 8B | `magic0='P'` / `magic1='L'` / `ver` / `type` / `seq`(u16) / **`group`** / `rsv[3]`（必ず 0） |
| 時刻 9B | 年月日時分秒 + 1/100 秒（GPS） |
| 位置・対地 12B | 緯度・経度 ×1e-7 度、対地速度 0.01m/s、真方位 0.01 度 |
| 高度・気圧 8B | GNSS 高度 / KF 高度（0.1m）、KF 昇降速度（0.01m/s）、気圧（0.1hPa） |
| 姿勢 11B | ロール・ピッチ・ヨー・平均ピッチ・ロールトリム（0.01 度）、ヨー精度95%（度） |
| 風 3B | 風速（0.1m/s）、風向（0.01 度、吹いていく方向） |
| 機体状態 6B | 電圧、捕捉数、水平精度（0.1m）、fix フラグ |
| ナビ設定 2B | `dest_index` / `nav_mode`（受信側が突き合わせて自動追従する） |
| 検査 6B | `have`（RHAVE_*）/ `status`（LINK_ST_*）/ `crc16` |

**版数は `LINK_PROTO_VER`。構造体レイアウトを変えたら必ず上げる。**
現在は **v3**（使われていなかった `tx_us`＝送信側 micros を `group` + 予備 3 バイトへ
置き換えた。受信側は自分の `millis()` で経過を測っており、`tx_us` を読む場所は 1 つも無かった）。
版が違うフレームは捨てるので、古いファームの機体を新しい受信機がミラーすることは無い。

異物の排除は **magic + ver + type + CRC16** の 4 つ。
**グループ ID はこの検査には含めない**（→ §1）。
検査で弾くと「電波は来ているがグループが違う」を無信号と区別できなくなるため、
`link_telem_valid()` は通し、表示に使うかどうかを **link.cpp が別に判断する。**

数値の丸めとクリップは `link_pack_*()` に 1 か所へ集めてある。
**NaN は 0 に落とす**（姿勢推定が発散したときに極値を送るより無害）。

受信側は受け取った内容を `received/` の CSV へ 1Hz で残す。
**姿勢・風の列名は `imu_replaydata/` と同じ**にしてあるので、
機体の SD が死んでも（`status` の `LINK_ST_SD_ERROR` がまさにその状態）
ボート側のログで ESKF の解析ができる。

**ペイロードを増やすと受信窓と送信電流の両方に直接効く。安易に足さないこと。**

`status` に載せるのは**「受信側からは知りようがない、送信機自身の健康状態」だけ**
（SD エラー・IMU エラー・トリム未適用・電池低下）。
飛行の警告（コース警告・バンク角警告・バリオ音）は**受信側がミラー値から自分で
再計算する**。計算が 1 本のままなので、送信側と受信側で挙動がずれる余地が無い。

## 5. 受信モードの画面と安全

- **どの画面にいても色付きの枠を出す。** 受信モードであることが常に分かるように。
- 地図の左上に**電波アイコンと役割アイコン**（船／飛行機）。受信モードは役割アイコンを点滅させる。
  **アイコンは送信モードでも出す。** 上りが無い以上、機体は届いたかどうかを
  知りようがないので、せめて「モジュールが生きていて送出できている」ことは見せる。
  枠とポップアップは受信モードだけ（表示の意味が入れ替わるのは受信側なので）。
- 電池は `S50R40%` の形で**送信側と受信側の両方**を出す。
  **送信機（機体）の電池低下は音声でも知らせる**（`wav/battery_low_sender.wav`、60 秒ごと）。
  本番では飛行中に交換できないが、試験飛行ではボートが先に気づいて降ろす判断ができるため。
  受信が切れると `link_sender_status()` が 0 を返すので、古い状態のまま鳴り続けることはない。
  SD／IMU／較正未適用の 3 つは従来どおり立ち上がりの低音 2 回だけにしてある
  （音声を増やすほど、本当に聞くべきものが埋もれる）。
- **10 秒受信が無ければ**「RECEIVER MODE. NO SIGNAL.」のポップアップを出し、
  自機の情報表示へ戻る。3〜10 秒の間は点滅させて「切れかけ」を示す。
- **NO SIGNAL 中もバリオを含めて全機能が動く。** 万一受信機モードのまま
  離陸しても使えるようにするため。
- ミラー ⇄ NO SIGNAL の遷移は音で知らせる。画面の数値の意味が
  「機体」と「自機」で入れ替わる瞬間なので、見ていなくても気づけるようにする。
- **目的地とナビモードは送信側に合わせて自動で上書きする**（RAM 上のみ）。
  食い違うとコース警告だけが静かにずれる。上書きしたことは必ず音声で知らせる。

### 電波アイコン

携帯電話と同じアンテナ本数表示。**枠 3 本（長さ違い）を常に描き、中を 0〜3 本ぶん塗る。**
塗りだけにすると 0 本・1 本のときに何の絵なのか読めなくなるため。

本数は**絶対値ではなく「限界からの余裕」で切る**。到達距離を決めているのは
`RSSI − 限界` であって RSSI そのものではないし、SF を上げれば限界も下がるので、
固定値のしきい値では SF を変えた瞬間に意味を失う。

```
限界 RSSI ≒ 環境雑音(実測 −104dBm) + SF の SNR 閾値
          = −111dBm (SF7)、SF が 1 上がるごとに −2.5dB
```

| 余裕 | 本数 | 色 | SF8 での目安 |
|---|---|---|---|
| 30dB 以上 | 3 | 緑 | > −83dBm |
| 20dB 以上 | 2 | 緑 | > −93dBm |
| 10dB 以上 | 1 | 橙 | > −103dBm |
| それ未満 | 0 | 橙 | ≦ −103dBm |
| 受信なし／モジュール無応答 | 0 + **赤い×** | 灰 | — |

- 判定に使うのは**直近 10 秒の平均 RSSI**。1 発ぶんは数 dB ふらつくので、
  瞬時値だと本数がちらついて読めない。
- 切れているときは 0 本アイコンの上に**赤い×**を重ねる。
  「弱い（0 本）」と「切れている」を色だけで区別させないため。
- 判定に使うアイコンは `src/flashdata/link_icons.cpp`（19×15 の 1bit マスク）。
  絵は `tools/gen_link_icons.py` で生成する。色は描画時に与えるので、
  同じ絵を強度に応じて緑／橙に塗り分けられる。

**★ 送信モードにアンテナ本数を出してはいけない。絵そのものを分ける。**

送信側には受信の手段が無い。強度を測っていないのに本数を出すと、
**測ったように見せることになる**。そこで送信モードは
**飛行機アイコンから出ていく電波の弧**（`ICON_TX0..3`）へ置き換える。

| 状態 | 絵 | 色 |
|---|---|---|
| 送出の直後（`LINK_TX_PULSE_MS` = 600ms 以内） | 弧 3 本 | 緑 |
| それ以外（待機中） | 弧 1 本 | 緑 |
| **一度も送れていない／モジュール無応答** | 弧 0 本 ＋ **赤い×** | 灰 |

弧は強度ではなく**脈動**である。1Hz 送信なので、**1 秒に 1 回膨らむのが正常**。
膨らみが止まったら送れていない。これなら「測っていないものを見せない」まま、
モジュールが生きて送出できていることだけを伝えられる。

### ボート自身の位置

ミラー中の地図は**機体**を中心に描くので、ボート自身は地図上に存在しない。
追走ボートにとっては「機体と自分がどれだけ離れているか」が知りたい情報なので、
自分の位置だけを小さく重ねる。

- **3px の点。** 機体マーカーより明らかに小さくして主役を取らせない
- **2m/s 以上のときだけ**進行方向へ 5px の線を伸ばす。
  停船中の GNSS の方位はでたらめなので、出すとかえって誤解を招く
- **色は明るい緑。** 飛行軌跡も緑（濃い）で、しかもミラー中の軌跡は機体のものなので、
  同じ色にすると埋もれて見つけられない
- ボート自身の航法は v6 以前の機体に任せる。受信機はあくまで「機体の画面の再現」

### 受信ログのリプレイ

`received/` は**リプレイ画面から再生できる**。一覧の `SOURCE` を
`RECEIVED (radio)` に切り替えると、走査するフォルダが `received/` に変わる。

- **一覧に出すのは常にどちらか一方だけ。** 混ぜないので、ページ計算も
  ファイル番号も「1 フォルダぶん」のままでよい（既存の計算に手を入れていない）
- 一覧の**並びはファイル名順ではなく、ディレクトリの登録順**（＝SD へ書かれた順）。
  上に出したいものはカードへ先にコピーする
- 走査するのは `data/`（自機）と `received/`（受信）だけ。設定用の CSV は
  ルート直下にしか無いので、**除外リストを持たなくてよい**
- 受信ログには**姿勢・風の列がそのまま入っている**ので、飛行 CSV のように
  `imu_replaydata/` を日付で引きに行く必要が無い。
  **★ 引きに行ってはいけない。** そこにあるのは**ボート自身の姿勢**なので、
  機体の航跡にボートのロール・ピッチが黙って合成される。
  判定は「CSV 自身が roll 列を持っているか」だけ
- 再生中は `REPLAY` ではなく **`REPLAY RX`** と出す。自機の飛行ではなく
  機体の飛行だと分かるようにするため
- **リプレイ中はミラーしない**（`link_mirror_active()` が false を返す）。
  再生を選んだのに生の受信データが出続けると「再生できない」ように見えるため。
  生データは `received/` に残り続けるので、再生を優先しても失うものは無い

> 受信モード中、**ルートの飛行 CSV にはボート自身のデータが記録されている**
> （位置・速度・方位は生のグローバル、気圧と高度は `_raw` の accessor）。
> つまり **画面に一度も出ていなかったボート自身の画面**も、あとから再生できる。

### ミラー中に止めること

**受信した機体の値を自機の推定へ入れてはいけない。**

- 自機のカルマン（`imu_kalman_gnss_update`）— 気圧基準と GNSS オフセットが壊れ、
  受信をやめた後まで残る
- `imu_replaydata/` の記録 — 受信した機体の日時のファイルに自機の姿勢を書いてしまう

## 6. E220 を扱う上での落とし穴

**★ 送信方法は必ずトランスペアレント（REG3 bit6 = 0）にすること。**
固定送信モードだと、モジュールは UART に来た先頭 3 バイトを
「宛先ADDH／宛先ADDL／チャンネル」として解釈する。すると環境ノイズ取得コマンド
`C0 C1 C2 C3 00 02` が**「宛先 0xC0C1・ch 0xC2 への送信データ」と誤解され、
コマンドが効かないどころか電波として出てしまう**。症状は「設定は完璧に入って
いるのに RSSI だけ永久に無応答、かつ AUX が Low に張り付く」。

我々の通信は同一チャンネルの全機が受け取るブロードキャストなので宛先指定は
元々不要で、トランスペアレントのほうが素直に合う（ヘッダ 3 バイトも消える）。

**書込みコマンド `0xC0` は不揮発メモリに保存されるので書換え寿命がある。**
起動時はまず `0xC1` で読み返し、一致していれば書かない。

- 起動時の 1 回だけ `0xC0`（不揮発）
- **設定画面での変更は `0xC2`（RAM のみ）**。CH を 0→12 と回すだけで 13 回に
  なるため。設定の正本は SD の `settings.txt` 側なので、次回起動時に
  同じ値が書き直される

**AUX は未接続・モジュール不在だと入力が浮いて Low に見える。**
「ビジー」と誤読すると永久に待つので、内部プルアップを入れて
居ないときは High（アイドル）に見えるようにする。

**コマンドの応答を先頭決め打ちで読まないこと。**
受信データやモード切替時のゴミが応答の前に乗る（実測で 69 バイト観測）。
`C1 + アドレス + 長さ` の並びを**検索**して拾う。

**環境ノイズの取得は mode 0 のまま行う＝受信と同じ UART を使う。**
ここで受信バッファを捨てると、**電波を確かめるための画面が受信を殺す**
（設定画面は 1Hz で問い合わせ、テレメトリも 1Hz で届く）。
応答とテレメトリを同じ組み立てバッファに入れ、応答の 5 バイトだけを抜くこと。
バッファを捨ててよいのは mode 3 に入っている間だけ。

## 7. 電波法

- **E220-900T22S(JP) は技適取得済み**で免許不要。920.6〜928.0MHz、最大 13dBm(20mW)
- **アンテナ利得は 3dBi 以下**（EIRP が 16dBm を超えられないため）。
  使用する `TX915-FPC-4510` は 2dBi
- **CH0〜12 に限る**（→ §2）
- キャリアセンス（LBT）はモジュールが必須機能として実装しており無効化できない
- **ボートから機体へ「操作」を送る機能は作らない。** 上りの通信路そのものが
  存在しない（→ §3）ので、遠隔で変更する経路は物理的に作れない

## 8. 実測

| 条件 | 設定 | 到達距離 | 限界RSSI |
|---|---|---|---|
| 芝生（凹凸あり） | 500k SF5 | 約 100 m | −89 dBm |
| 同上 | 500k SF8 | 約 190 m | −99 dBm |
| **海辺・平坦なコンクリート・夜間** | **500k SF7** | **約 350 m** | −100〜−110 dBm |

- 環境雑音は**熱雑音 +7dB（BW500kHz で約 −104dBm）**。屋内外でほとんど変わらない
- **要求 200m を 1.75 倍で満たした**
- 限界 RSSI は「環境雑音 + SF の SNR 閾値」と**見通しの良い地点でのみ**一致する。
  SF7・海辺の −110dBm は理論値 −111dBm とほぼ一致したが、芝生の SF8 は
  −99dBm で止まった。後者は感度ではなく地形（フレネル半径・多重反射）で
  切れている。**アンテナ本数の表示は理論値を基準にしているので、
  地形が悪い場所では 1 本のまま切れることがある**（→ §5）
- **1 回目と 2 回目の差（100m→350m）は SF では説明できない。**
  SF5→SF7 の利得は 5dB で距離にすると 1.3〜1.8 倍にしかならず、
  残りを説明するにはさらに 6〜17dB 相当が要る。
  設置条件（平坦なコンクリート／アンテナの置き方）か地点の雑音差か、その両方。
  **この 2 回のデータでは切り分けられない**

### アンテナは SF より効く

**アンテナの角度で RSSI が変動し、パケットロストが始まる**（実測）。
偏波ミスマッチの損失は 45°ずれで 3dB、60°で 6dB、80°で 15dB。
**SF を 1 段上げても 2.5dB** しか稼げない。

低いアンテナ同士では、ある距離から先は損失が距離の 2 乗ではなく **4 乗**で増える
（2 波地面反射）。受信電力は `(h1×h2)²` に比例するので、
**高さ 1m/1m → 2m/2m で +12dB、1m/1m → 3m/10m で +30dB**。
プラットフォームは 10m の高さがあるので、アンテナを最上部に出すだけで
最大の効果が無料で得られる。
