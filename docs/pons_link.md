# PONS Link — 機体⇄ボート テレメトリ無線仕様書

同一ファームウェアの PONS を 3 台製作し、設定により役割を決定します。

| 役割 | 台数 | 設置場所 | 動作概要 |
|---|---|---|---|
| **送信機 (TX)** | 1 | 機体 | パイロット用航法装置。1Hz（アッパーバンドでは約 1.2〜3.5s）でテレメトリを送信 |
| **受信機 (RX)** | 2 | 追走ボート / プラットフォーム | 受信テレメトリにより機体画面を完全ミラー表示。送信は行わない（下り一方向） |
| **予備機** | (1) | プラットフォーム | 機体トラブル時に TX へ切り替えて換装。通常時は RX または OFF |

通信は**下り一方向のみ**であり、受信側から機体への遠隔操作経路は物理的に存在しません（大会レギュレーション適合・安全設計）。

---

## 1. 役割とモード

### 1.1 モード切替と音声読み上げ
* `settings.txt` の `link_mode`（`OFF` / `TX` / `RX`）で決定。
* 設定変更時および起動時には **3 状態すべてを音声で読み上げる**（`sender_mode.wav` / `receiver_mode.wav` / `link_off.wav`）。
  - 「無音＝OFF」にすると、音量ゼロや音声ファイル欠損と区別がつかず、送信機が電波を出したままになる事故を防ぐため。
* スイッチ操作による設定画面（WIRELESS LINK）は 3 択トグルのため「送受同時 ON」は原理的に起こり得ない。

### 1.2 グループ ID (`link_group`)
* 他チームの PONS との混信を避ける識別子（0〜255、既定 0 は git 管理用。本番値は現地 SD で設定）。
* ペイロード内の ID で識別するため、モジュール設定の書き換えは不要。
* グループ不一致のフレームを受信した場合、無信号とは区別して `Signal : GROUP X FOUND` と表示し、SD 設定ミスに気づけるようにする。受信機側で他グループへの自動スキャンは行わない（待機チャンネルを外すリスクを避けるため）。

### 1.3 重複送信機検出 (`DUP SENDER`)
* 同一 CH / SF / Group 内で 2 台の送信機が稼働した場合、`seq` の逆行・停滞（同一 seq や小さな戻り）を検知。
* 画面に `DUP SENDER !! / 2 TX ON SAME CH/GROUP` 赤ポップアップを表示し、音声で警告（1 分ごと）。
* 2 台目を停止すれば 30 秒で自動消去（永久ラッチにしない設計）。

## 2. 無線とハードウェア

モジュールは **E220-900T22S(JP)**（920MHz LoRa、技適取得済、免許不要、送信出力 13dBm / 20mW）を使用します。

### 2.1 チャンネルと帯域構成（BW 500kHz 固定）
帯域幅 500kHz が重ならないよう、0.6MHz（アッパーは 1.2MHz）離して割り当てます。

| 項目 | ローワーバンド（標準運用） | アッパーバンド（混雑時退避用） |
|---|---|---|
| **使用チャンネル** | **CH0 / 3 / 6 / 9 / 12**（5 チャンネル） | **CH15 / 21 / 27**（3 チャンネル） |
| **周波数** | 920.8 / 921.4 / 922.0 / 922.6 / 923.2 MHz | 923.8 / 925.0 / 926.2 MHz |
| **帯域幅 (BW)** | 500 kHz 固定 | 500 kHz 固定 |
| **拡散率 (SF)** | **SF8（既定）**、SF7〜SF11 | SF7〜SF10（**SF11 は選択不可**） |
| **送信間隔** | 1.0 秒固定（休止 50ms） | SF7: 1.0s / SF8: 1.2s / SF9: 2.0s / SF10: 3.5s |
| **電波法制約** | 休止時間 50ms 固定 | 1 回 400ms 以下、送信時間の 10 倍休止、1h 内 360s 以下 |

※ アッパーバンドでは電波法により「送信時間の 10 倍休止」が強制されるため、送信完了後にモジュールが自動で休止に入ります。SF11 は送信時間（約 358ms）が 400ms 上限に近すぎるため選択不可としています。

### 2.2 ハードウェア結線
| 信号線 | RP2350 ピン | ネット名 | 備考 |
|---|---|---|---|
| UART1 TX | **GPIO8** | `LORA_TX` | E220 RXD へ接続（115200bps 8N1） |
| UART1 RX | **GPIO9** | `LORA_RX` | E220 TXD から受信 |
| AUX 入力 | **GPIO30** | `LORA_AUX` | モジュール状態監視（100nF で GND へバイパス） |
| M0 + M1 | **GPIO31** | `LORA_M01` | 1 ピンで同時駆動（Low = mode 0, High = mode 3） |

## 3. タイミングと省電力

### 3.1 送信時間と消費電流（32 バイト固定フレーム）
送信機は 1 秒周期のうち、送信時のみ mode 0 で起動し、送信完了後に mode 3（高速スリープ・約 2µA）へ落とすことで平均消費電流を大幅に低減します。受信機は常時 mode 0（約 8.2mA）で待機します。
32 バイトフレームにおける送信時間（`e220_airtime_ms()`）と見込み値・消費電流は以下のとおりです。

| 拡散率 | 送信時間（理論計算値） | **AUX Low 時間（見込み）** | 平均電流（1Hz 送信時） | 電波占有率 (1Hz) |
|---|---|---|---|---|
| **SF7** | 42 ms (41.5 ms) | **約 65 ms** | 約 2.5 mA | 4 % |
| **SF8（既定）** | **70 ms (70.3 ms)** | **約 105 ms** | **約 4.0 mA** | **7 %** |
| **SF9** | 120 ms (120.1 ms) | **約 180 ms** | 約 7.8 mA | 12 % |
| **SF10** | 209 ms (209.4 ms) | **約 315 ms** | 約 13.5 mA | 21 % |
| **SF11** | 358 ms (357.4 ms) | **約 536 ms** | 約 23.0 mA | 36 % |

> ### ★★ 重要: AUX Low の時間は計算値の約 1.5 倍（見込み）
> ARIB のキャリアセンス時間および内部処理により、モジュールが塞がる実時間（AUX Low）は送信時間計算値の約 1.5 倍になる見込みです（65 バイト時の実測に基づく）。
> **送信完了（AUX High 復帰）を見る前に mode 3 へ落としては絶対にいけません。**（送信を終える前に落とすと受信側でパケットが 90% 以上ドロップします）。

### 3.2 ノンブロッキング送信ステートマシン
Core0 をブロックさせないため、送信処理は 4 段階のステートマシンで回します:
1. `LTX_IDLE`: 1 秒経過で `e220_wake_begin()`（mode 0 設定）→ `LTX_WAKING`
2. `LTX_WAKING`: 起床完了（AUX の Low を見てから High）で UART 送信 → `LTX_TXSTART`
3. `LTX_TXSTART`: AUX が Low へ落ちる（送信開始）を確認 → `LTX_TXDONE`
4. `LTX_TXDONE`: AUX が High へ復帰（送信完了）した瞬間に `e220_sleep()`（mode 3）→ `LTX_IDLE`

## 4. UART と電波に載せるもの

### 4.1 送信パケットの一括 write
宛先 3 バイト（`00 00 <ch>`）＋ データ 32 バイトの計 35 バイトは、**1 回の `Serial1.write()` で隙間なく一括送信**します。書き込みが途切れると E220 が別パケットに分割発射して受信側で壊れます。

### 4.2 電波上の 32 バイト固定フレーム（形式 2, `0xA2`）
| バイト | 内容 |
|---|---|
| **0** | マジックバイト `0xA2`（形式 2 の印） |
| **1** | `seq`（シーケンス番号下 8 ビット） |
| **2** | `group`（グループ ID） |
| **3 - 4** | `status`（送信機健全性フラグ） |
| **5** | `flags`（データ有効ビット: Fix, 速度, 高度, 昇降, 姿勢, 時刻） |
| **6 - 7** | エポック内 0.1 秒時刻（0〜35999） |
| **8 - 15** | 緯度・経度（各 4 バイト符号付き整数、1e-7 度刻み） |
| **16 - 18** | 対地速度 12bit（0.025m/s 単位）＋ 真方位 12bit（0.1° 単位） |
| **19 - 20** | KF 高度（0.1m 単位） |
| **21** | KF 昇降速度（0.05m/s 単位、±6.35m/s 飽和） |
| **22 - 26** | ロール（0.1°）、ピッチ（0.1°）、ヨー（0.1°） |
| **27 - 29** | **回転枠データ**（`seq % 8` により 8 発で 1 周） |
| **30 - 31** | CRC16-CCITT（バイト 0〜29 対象） |

### 4.3 回転枠（8 秒周期で低頻度データを循環送信）
- **枠 0**: 年・月・日・時（JST）
- **枠 1**: 10 秒平均ピッチ、ヨー精度（Y95）
- **枠 2**: 自動ロールトリム累積量、推定風速
- **枠 3**: 推定風向（真方位）、GNSS 捕捉衛星数
- **枠 4**: GNSS 生高度、電池電圧
- **枠 5**: 大気圧、地図縮尺（`scale_index`）
- **枠 6**: 水平位置精度（hAcc）、目的地番号
- **枠 7**: ナビゲーションモード、**目的地 ID (`dest_id`)**

※ 風速（枠 2）と風向（枠 3）は**両方を受信して初めて有効化**し、受け始めに 0° を出さない安全設計としています。また hAcc（枠 6）も受信前は未知（0xFFFFFFFF）として扱い、誤って精度良好と誤認するのを防ぎます。

## 5. 受信モードの画面と安全

### 5.1 ミラー表示中の完全分離原則
受信モード中は画面上の数値が機体のものに切り替わりますが、**警告や自機の状態が混入する事故**を防ぐため厳密に分離されています。

| 項目 | ミラー中に参照する対象 | 理由・動作 |
|---|---|---|
| **較正要求（赤字 / Pavg 取消線）** | **送信機の** `LINK_ST_NEEDS_APPLY` | 自機の較正状態は無関係 |
| **`ESKF Not ready`** | **非表示** | 自機の未収束で機体の姿勢表示を消さない |
| **姿勢・風・バンク警報** | **送信機の** `Roll/Pitch/Yaw func` | 送信機の設定で表示・警報 |
| **昇降計（VSI バー・バリオ音）** | **送信機の** V/S | **自機の気圧や IMU で鳴らさない**（波の揺れでの誤鳴動防止） |
| **MAX G/S** | **送信機の** 対地速度 | 自機ボートの最高速を混入させない |
| **GNSS 速度途絶の取消線 / 風の ×** | **送信機の** `LINK_ST_GNSS_LOST` | ボート側のトンネル等で機体表示に線を引かない |
| **地図の縮尺** | **送信機の** `scale_index` に自動追従 | 送信機と同一の視野を共有。手動変更は低音2連で引き戻す |
| **地上チェック音声** | **送信機の** `LINK_ST_GROUND_*` | 自機ボートの揺れで地上警告を誤発報しない |
| **`NO GNSS connection !!`** | **非表示**（音とログのみ） | 画面の主役は機体のため |
| **`POWER FAULT !!` / `PWR!`** | **自機で判定して表示**（唯一の例外） | 自機ハードの発熱・焼損リスクを警告するため |

### 5.2 目的地の照合（`dest_id` による自動追従）
目的地の並びは「内蔵 4 つ（PLATHOME / N_PILON / S_PILON / TAKESHIMA）＋ SD の `destinations.csv`」で構成されます。番号（`dest_index`）だけで合わせると、CSV の中身や並びが食い違っている場合に受信機が黙って別の場所に合わせてしまう重大事故につながります。
そのため、32 バイトフレームの回転枠 7 に**目的地 ID（`dest_id`: 名前と座標の CRC16）**を載せて照合します（`link_sender_dest_local()`）。
- **受信機に同一 ID の目的地がある**: その目的地番号へ自動同期（番号が違っても位置が合っていれば同期）。
- **受信機に該当 ID が存在しない**: **受信機を「目的地なし」へ倒す**（誤った目的地によるコース警告・誘導線・距離の表示を防止）。低い 3 連トーン（294Hz）とログ `LINK: sender dest not on this unit` で通知し、WIRELESS 画面に `Dest : NOT IN THIS UNIT`、地図に `SENDER DEST NOT IN THIS UNIT` を表示。
- **`dest_id == 0`**: ID 未送信（古い機体等）とみなし、従来どおり番号で追従。

### 5.3 リプレイ中・デモ中の無線抑制（`link_rf_suppressed` / `link_live_ui_ok`）
再生中の過去データやシミュレータの仮想機体を電波に流したり、画面表示を誤認させないため、2 つの述語で厳密に制御します。
| 述語 | 状態 | 影響範囲・動作 |
|---|---|---|
| **`link_rf_suppressed()`** | リプレイ中 or デモ中 | **送信（TX）を完全停止**（`link_tx_tick()` 早期 return）。WIRELESS 画面に `Hold : replay (no TX)` 表示 |
| **`link_live_ui_ok()`** | `!link_rf_suppressed()` | 受信枠、`NO SIGNAL` 箱、S/R 2本立て電池、ミラー切り替えトーンを抑止（「OFF 扱い」画面にし、`link_mode_setting` 自体は保持） |

### 5.4 電波強度・フェイルセーフ
* **受信機 (RX)**: 携帯電話型のアンテナ本数（0〜3 本）。到達限界 RSSI（環境雑音 −104dBm ＋ SNR 閾値）に対するマージンで判定。
* **送信機 (TX)**: 受信手段が無いためアンテナ本数は出さず、電波の弧の脈動（1 秒に 1 回）のみを表示。
* **10 秒途絶フェイルセーフ**: 10 秒間無信号が続くと `NO SIGNAL` ポップアップを出し、自機航法（自機 GNSS・気圧）へ自動復帰。音声「受信が途切れました。自機の情報を表示します」を発報。

## 6. E220 を扱う上での落とし穴

実機ブリングアップで必ず踏むハードウェア・プロトコルの罠と対処法です。

### 6.1 起床時は AUX の立ち下がりを確認する
`digitalWrite(E220_MODE_PIN, MODE_NORMAL)` で mode 0 を指示した直後、AUX がまだ High のままに見える時間（約 1〜2ms）が存在します。
**Low（セルフチェック開始）を一度も確認せずに High だからと即座に UART 送信すると、コマンドやパケットがモジュール内部で黙って破棄されます。**
`e220_wake_ready()` では、AUX が Low に落ちたことを確認してから High に戻るのを待つか、セルフチェック遷移全体を覆う `E220_WAKE_SETTLE_MS`（20ms）の経過を保証しています。

### 6.2 mode 3 への遷移と安定待ち（`enter_config_mode()`）
mode 3 への切替後も AUX High を待つだけでなく、UART 安定時間 `E220_CFG_SETTLE_MS`（30ms）待ってから通信を開始する必要があります。
切替直後はモジュール内部のボーレート再設定等で 1 バイト目が化けるため、これらは `enter_config_mode()` にカプセル化されています。

### 6.3 ver.1 互換環境ノイズコマンドの電波発射罠
E220 ver.1 仕様書にある `C0 C1 C2 C3 00 02` をファームウェア v2.0 に送ると、**返事がゼロなだけでなく、直後に AUX が Low に落ちてこの 6 バイトがそのまま電波として発射されます。**
正しいコマンドは mode 0 のまま送る `FF FF C1 A3 01` です。

### 6.4 mode 3 で環境ノイズを読んではいけない
mode 3 では `0xC0` / `0xC1` は「レジスタ書き込み」と解釈されるため、環境ノイズ取得コマンドを送るとモジュールが以降のコマンドをすべて書き込みデータとして解釈しフリーズします。環境ノイズは必ず mode 0 で読みます。

### 6.5 Strict Mode の必須設定と EEPROM 寿命保護
* 環境ノイズレジスタ（`0xA3`）の読み出しには、レジスタ `0x09` bit6 の Strict Mode（`0xC1` コマンド応答許可）が必須です。
* 通常のチャンネル切替や一時設定には RAM 一時書き込みコマンド `0xC2` を使用し、EEPROM 書き込み `0xC0` は初回のみ行うことでフラッシュ寿命を保護します。

### 6.6 UART 応答の先頭ゴミ読み飛ばし
モード切替直後は UART FIFO に 1 バイトのゴミ（`0x00` や `0xFF`）が乗る場合があります。固定バイト数で打ち切らず、応答ヘッダ（`FF FF C1` 等）が見つかるまで読み飛ばす実装が必要です。

### 6.7 AUX は未接続・モジュール不在だと入力が浮いて Low に見える
AUX ピンはモジュール未実装または断線時にフローティングとなり Low に見えやすくなります。「ビジー」と誤読して永久待ちに入るのを防ぐため、マイコン側で内部プルアップを設定し、モジュール不在時は High（アイドル）に見えるようにしています。

### 6.8 環境ノイズ取得時に受信バッファを捨ててはいけない
環境ノイズの取得（`0xA3`）は mode 0 のまま行うため、受信と同じ UART を共用します。ここで受信バッファをフラッシュして捨てると、電波を監視・調査するための処理が本来のテレメトリ受信を破壊します。また AUX が Low（送受信中）の場合はノイズ取得を見送る必要があります。

## 7. 電波法適合（ARIB STD-T108）

* **ローワーバンド**: 送信休止時間 50ms 固定。400ms 制限や 10 倍休止は不要。1Hz 送信が可能。
* **アッパーバンド**: 1 回の送信時間 400ms 以下、送信時間の 10 倍の休止時間、および 1 時間あたりの総送信時間 360 秒以下が義務付けられています。
  - PONS では SF ごとに送信間隔を自動調整（SF8 で 1.2 秒、SF10 で 3.5 秒）し、SF11 は使用禁止とすることで完全適合しています。

## 8. 実測性能（琵琶湖畔・地上試験）

### 8.1 到達距離と RSSI
海辺・平坦コンクリート環境にて **約 350m（SF7）** の安定通信を確認（要求 200m の 1.75 倍）。

| 距離 | RSSI 中央値 | 受信率 | 備考 |
|---|---|---|---|
| 0〜20 m | −60 dBm | 100% | 至近距離 |
| 20〜40 m | −88 dBm | 100% | |
| 40〜80 m | −92 dBm | 98% | |
| 80〜100 m | −102 dBm | 94% | |
| 100〜130 m | −113 dBm | 72% | アンテナ 1 本ライン（限界付近） |
| 130〜145 m | −113 dBm | 24% | パケットドロップ急増 |

### 8.2 環境雑音の実測値
琵琶湖畔での環境雑音は BW 500kHz で実測 **−104 dBm**。これに SF8 の所要 SNR（−9dB）を加えた **−113 dBm** が理論受信限界となり、実測距離と完全に一致しています。

### 8.3 アンテナ設置の物理要件
1. **高さの効果（2 波地面反射）**: 受信電力はアンテナ地上高の積 $(h_1 \times h_2)^2$ に比例。地上高 1m/1m → 3m/10m（ボート/プラットフォーム）で **+30dB** のゲイン。
2. **偏波の一致**: 垂直偏波（真上向き）を維持すること。傾き 60° で 6dB、80° で 15dB の大損失となる。

## 9. 運用チェックリスト（大会当日）

1. **出艇前**: 送信機・受信機の `link_group`、`channel`、`profile (SF)` が一致していることを WIRELESS 画面で確認。
2. **送信前チェック (`Preflt`)**: TX 起動時に `Preflt : OK` が出ることを確認（BUSY や NOISY の場合はチャンネル変更）。
3. **受信機動作確認**: ボート側で機体の画面がミラー表示され、電波アイコンが緑（2〜3 本）であることを確認。
